# G4 本地端口契约

`contracts/local/g4.md` · owner: G4 · 状态：draft（阶段 A 冻结待评审）

本文件定义 reservation-service 内部、G4 对外提供的 Java 端口。这些端口**不经过网络**，
只在同一进程、同一 Spring 装配内调用。

- 依据：技术文档 v2.0 §5.8（同进程公开应用端口）、§2.3（本地事务边界）、§7.1（锁顺序）。
- 共同约束：本地事务内调用，**无网络重试**；技术异常向上抛并回滚；明确业务拒绝通过
  返回联合表达，不把所有拒绝都抛异常。
- `TxContext` 由协调器创建，**不能由 HTTP 正文注入**。
- 只读方法不带 `TxContext`。
- 所有列表返回分页结构，不返回无界实体。

## 1. 跨模块依赖：G4 调用的外部端口

协调器在**事务外**调用 G1 的定位端口：

```java
// G1 提供，G4 集成协调器调用
interface ReservationLocatorPort {                       // G1-L07
    ReservationLocation locate(Id reservationId, ResourceCaller caller);
}

record ReservationLocation(Id reservationId, Id roomId, Id seatId, Id ownerId, Version version) {}

sealed interface ResourceCaller {
    record User(Principal principal, Action action) implements ResourceCaller {}
    record SystemRepair(ServiceName callerService, Id roomId, Id sourceId, Id operationId) implements ResourceCaller {}
    record SystemDue(Task task) implements ResourceCaller {}
}
```

约束（违反即为缺陷）：

- **事务外、无锁只读**。拿到 `roomId` 后由协调器锁 G4 房间行，再让 `G1-L02` 在同事务
  重读并核对 `reservationId / roomId / seatId / ownerId` 与快照一致；不一致
  `409 SNAPSHOT_MISMATCH` 回滚。
- **不得先锁 G1 预约行再锁房间**。
- 映射缺失或用户不可见返回 404，不得绕过 G1 直接查表。

## 2. G4-L01 `AvailabilityPort.search`

```java
interface AvailabilityPort {
    // 基线签名：单一入口，kind 判别返回类型
    AvailabilityPage search(Principal principal, AvailabilityQuery query, Kind kind);  // kind = ROOM | SEAT
}

record AvailabilityQuery(
    Page page,
    Time start,
    Time end,
    Id roomId,              // 可空
    String seatCode,        // 可空
    String area,            // 可空
    Socket[] socketTypes    // 空数组意为未筛选
) {}

// Java 无法按 kind 重载返回类型，用密封结果表达；语义与基线等价。
sealed interface AvailabilityPage {
    record Rooms(PageResult<RoomAvailability> page) implements AvailabilityPage {}
    record Seats(PageResult<SeatAvailability> page) implements AvailabilityPage {}
}
```

**这是系统内唯一的可用性判定入口**，G1 不得自行拼装可用性逻辑。
「单入口 + 密封结果」是把基线签名落地到 Java 的方式；若改为两个独立方法，
属于契约变更，需 G1 评审确认（见 g4.yaml open_questions Q2）。
- 权限：`room:read` + `canAccessRoom`。
- 原因判定顺序固定（见 `resource-types.yaml` 的 `UnavailableReason`）：
  房间有效 → 座位有效 → 访问院系 → 完整开放 → ADMIN → REPAIR → WHOLE → PERSONAL。
  任一命中即不可用，可同时返回多项。
- 多个限制独立叠加，**解除一项不能 `available=true` 覆盖其他项**。
- `availableSeatCount` 按实际限制计算，**不能用登记座位总数代替**。
- 只对当前用户可见的数据计算；公开结果只显示类别，不含他人身份、用途、sourceId。
- 空数组 `socketTypes` 只在本本地字段表达"未筛选"；HTTP query 层不得用空值表达，需 400。

## 3. G4-L02 `ResourceTransactionCoordinator.execute`

**reservation-service 内所有改变资源可用性的动作的唯一写事务入口。**

```java
interface ResourceTransactionCoordinator {
    TransactionOutcome execute(ResourceTransaction command);   // G4-L02

    Room createRoom(Principal principal, CreateRoomRequest input, Id key, Id traceId);              // G4-L09
    Seat createSeat(Principal principal, Id roomId, CreateSeatRequest input, Id key, Id traceId);   // G4-L10
    Claim releaseAdmin(Principal principal, Id claimId, ReasonBody input, Id key, Id traceId);      // G4-L11
}
```

- 调用方为 G4 公网控制器，**仅 G4 写本域**。
- 新房间先按编号互斥与唯一约束创建记录，事务中取得该新 room 锁；
  L10 / L11 先取得现有 room 锁。**三者都不经过 G1，也不锁用户。**
- 三方法完整继承所列公网接口（P02 / P09 / P13）的鉴权、错误、幂等与状态语义；
  院系事实在事务外准备，在入口验证。
- **L02 与 L09—L11 共同构成唯一资源事务边界，禁止绕过它们写 G4 资源。**

### 3.1 命令联合

```java
sealed interface ResourceTransaction {
    record CreatePersonal(Principal principal, CreatePersonalBody body, Config config,   // config 可空
                          Id key, String requestDigest, Id traceId) implements ResourceTransaction {}

    record PersonalAction(Principal principal,      // 后台可为 null
                          Id reservationId,
                          Action action,            // CANCEL | CHECKIN | DUE
                          PersonalActionBody body,  // expectedVersion 可空、reason 可空、roomCode 可空
                          Id key, Id traceId) implements ResourceTransaction {}

    record ResourceChange(Principal principal, Id roomId, Version expectedVersion,
                          ResourceChangeSpec change, Id impactToken,
                          List<AccountFact> accountFacts, Time factsValidUntil,
                          Id key, Id traceId) implements ResourceTransaction {}

    record ClaimCommand(ClaimCommandBody command, SourceType sourceType, // M2 | M3
                        Id sourceId, Eligibility eligibility) implements ResourceTransaction {}

    record Expire(ExpireIfNotApprovedBody body, Id sourceId) implements ResourceTransaction {}
}
```

### 3.2 结果联合

```java
sealed interface TransactionOutcome {
    record NeedsConfig() implements TransactionOutcome {}
    record ReservationDisposition(Disposition disposition,      // CREATED | REPLAYED | APPLIED
                                  ReservationView reservation) implements TransactionOutcome {}
    record ResourceResult(Id roomId, Version version, int affectedCount) implements TransactionOutcome {}
    record ClaimResultOutcome(ClaimAdjudication adjudication) implements TransactionOutcome {}
    record ExpiryOutcome(ExpiryVerdict verdict, ClaimResult result) implements TransactionOutcome {}
}
```

### 3.3 锁顺序（不可调换）

| 路径 | 顺序 |
|---|---|
| `CreatePersonal` | `reservation_user_lock(userId)` → `room` 行 → G1 预约/违约行 或 G4 来源行（同类型按 ID 升序） |
| 其他全部路径 | 从 `room` 行开始，**不取用户锁** |
| 铁律 | 已持 `room` 锁的路径**不得**再请求用户锁 |
| 多房间 | 一次只接受一室；后台批量按 `roomId` 升序逐室开独立事务 |
| `PersonalAction` | 事务外 `G1-L07` 定位 → 取 `room` 锁 → `G1-L02` 回验 |

补充：所有 claim 检查/插入、房间归属/开放/停用变更、新座位写入，都必须持该房间锁；
用户锁只用于串行"同一人跨房重叠检查"；取消不取用户锁（只减少集合，不会制造重叠）；
截止/签到/维护共用同一把 room 锁，**锁后刷新时钟**。

### 3.4 事务内执行顺序

```
事务外：核验身份 / 参数 / 资格（G5 事实有效期 5 秒）
  ↓ 开事务，按 §3.3 加锁
validate：version / 预览 token / 事实是否过期
  ↓
G1 结算已到期记录
  ↓
G4 验证或建立新来源（写 claim）
  ↓
G1 写自身创建 / 签到 / 系统取消
  ↓
G4 按 G1 返回释放个人来源、失效受影响 WHOLE
  ↓
各 owner 写历史 + outbox
  ↓
一次提交
```

- 技术失败整体回滚；**`WHOLE` 批准的确定业务拒绝不算技术失败**，走 `G4-L12` 写拒绝
  事实并正常提交。
- 不得在事务内发起网络调用。
- 不得对外出现"半封锁、半取消"。

### 3.5 `CreatePersonal` 的 `NEEDS_CONFIG` 分支（最易写错）

1. 命中重放 → 直接返回 `ReservationDisposition(REPLAYED, 原 ID 当前记录)`，**不再请求新 Config**。
2. 索引 `ABSENT` 且 `config == null` → 返回 `NeedsConfig`。**返回前必须结束探查事务、
   释放全部锁**，且不写预约、claim、creation_intent、成功历史、outbox（幂等创建的用户锁
   基础行不算业务受理）。
3. G1 收到 `NeedsConfig` 后在事务外取配置，再用**相同的 `key` / `requestDigest` / body /
   主体**重入。失败返回 503 且不创建业务记录。
4. 事务内**最终复查**用户锁内的索引：同键命中 → `REPLAYED`；确认 `ABSENT` 且已给
   Config → 原子提交后返回 `CREATED`。
5. `NeedsConfig` **不映射成成功或 202，不产生 operationId**；不得因预查 `ABSENT`
   就跳过用户锁内复查。

## 5. G4-L05 `ResourceLedgerPort.apply`

```java
interface ResourceLedgerPort {
    LedgerOutcome apply(TxContext ctx, LedgerMutation mutation);        // G4-L05
    ClaimAdjudication recordDecline(TxContext ctx, Id sourceId,          // G4-L12
                                    ClaimCommandBody command, Error error);
}

sealed interface LedgerMutation {
    record CheckOnly(Ref source, Id seatId, Time start, Time end) implements LedgerMutation {}
    record Activate(Ref source, Id seatId, Time start, Time end,
                    Version sourceVersion, Id operationId, String reason, Time effectiveAt) implements LedgerMutation {}
    record Release(Ref source, Version sourceVersion, Id operationId, String reason,
                   Time effectiveAt, Terminal terminal) implements LedgerMutation {}
}

sealed interface LedgerOutcome {
    record Value(ClaimResult result) implements LedgerOutcome {}
    record BusinessRefusal(Error error) implements LedgerOutcome {}
}
```

`seatId` 取值矩阵（**硬约束**）：

| 来源 | `seatId` |
|---|---|
| `PERSONAL` | 必须是本室座位 ID |
| `WHOLE` | 必须 `null`，作用整间（含之后新增座位） |
| `REPAIR` | 必须 `null`，作用整间（含之后新增座位） |
| `ADMIN` | 可 `null`（整间）或本室座位 ID（单座） |

- `CHECK_ONLY` 成功返回 `Value`，其中 `state=ABSENT`、`claimId=null`、`effectiveAt=null`、
  `resultVersion=room.version`、`rejection=null`；**只检查，不建来源**。
- 冲突返回 `BusinessRefusal`，**不抛异常**。
- `ACTIVATE` / `RELEASE` 只有 G4 写台账与历史；资格与业务规则由协调器及各 owner 已校验。
- 非 `null` 的 `seatId` 必须确属该 `roomId`，否则拒绝；**禁止把单座 ADMIN 清空成整室**。

`recordDecline` 接受三种映射，且**必须在同事务内**与原输入摘要、sourceVersion、
原 HTTP 409/422 及完整 `Error`（`details.operationId` = 本 operationId）、拒绝时刻、
operation 结果、来源墓碑/历史与审计一并提交；返回 `DECLINED`，HTTP 状态在提交后才映射。

| 拒绝码 | 来源终态 | HTTP |
|---|---|---|
| `RESOURCE_CONFLICT` | `REJECTED` | 409 |
| `QUALIFICATION_REVOKED` | `REJECTED` | 422 |
| `DEADLINE_PASSED` | `EXPIRED` | 422 |

**不得用于**暂时网络失败、旧版本、快照不一致或未到截止——这些错误不推进来源终态。
资格否定也须在 5 秒内的事实与同一 roomVersion 下成立；事实过期先回滚重验，
不能伪造确定拒绝。重复原 operation 返回持久原裁决。

## 9. G4-L07 / L08 运行与异常

```java
interface OperationReadPort {                                   // G4-L07
    PageResult<Operation> list(Principal principal, OperationQuery query);
    Operation get(Principal principal, Id id);
    Metrics metrics(Principal principal, Id roomId);
}
interface OperationRecoveryPort {                               // G4-L08
    Operation retry(Principal principal, Id id, ReasonBody body, Id key);
}
```

- owner 只能查询与写入本组操作表。
- 重试**只重新排队 owner 的原操作**，不能改决定、手改他组数据或跳过范围检查。
- 聚合分页在同 schema 只读 `REPEATABLE READ` 事务内调用两个 owner 端口，各端口用同一
  过滤条件、`createdAt` 降序 / `id` 升序，从第 1 页起每次 100 条归并，丢弃前
  `(page-1)*pageSize` 项后取一页；`total` 取两个 owner 过滤计数之和。

## 11. G4-L11 `releaseAdmin`

基线签名（技术文档 §5.8）：

```java
Claim releaseAdmin(Principal principal, Id claimId, ReasonBody input, Id key, Id traceId);
```

- `ReasonBody = {expectedVersion: V, reason: S[1,1000]}`，`expectedVersion` 必填——
  缺失即丢失乐观并发控制，与其他更新接口的约定一致。
- 语义：只释放 `ADMIN` 本来源的占用；G4 写释放时间；重复原键返回原结果；
  其他来源 `403`；不删除维修或占用产生的其他来源限制。
- 与其他三个方法一样，先取得现有 room 锁，不经过 G1、不锁用户。

## 12. 消费方契约测试要求

阶段 A 冻结后，各消费模块必须用共享 fixture 跑消费者契约测试（技术文档 §10.1）：

| 消费方 | 必须覆盖 |
|---|---|
| G1 | `L01` 查询语义与原因顺序、`L02/CreatePersonal` 的 `CREATED`/`REPLAYED`/`NEEDS_CONFIG` 三分支、`L03` 切片形状、`L04` 含停用对象 |
| G1 后台任务 | `L02/PersonalAction` 的 `DUE`，`principal=null` 且固定系统执行者 |
| G4 自身 | `L05` 的 seatId 矩阵与 `BusinessRefusal` 不抛异常、`L06` 的 `IMPACT_CHANGED`、`L12` 三种映射（409/422/422）提交后返回、`L09`—`L11` 只能经由协调器写本域 |
| G2 / G3 | 不直接调用本地端口；通过 `G4-I04`—`I07` 的 HTTP 契约测试覆盖 |

反例（必须被拒绝并记录在测试报告里）：

- `REPAIR` / `WHOLE` 带非 `null` 的 `seatId`。
- `PERSONAL` 带其他房间的 `seatId`。
- 单座 `ADMIN` 被"清空"成整室。
- 已持 `room` 锁后再请求 `reservation_user_lock`。
- `NEEDS_CONFIG` 被映射成 200 / 201 / 202。

## 13. 契约自检（可复现命令）

在 CI 尚未建立前，用下面两条命令证明契约可用。**版本必须锁死，禁止用 `latest`**
（技术基线 §1：初始化时锁补丁版本和镜像摘要，不用 latest）。

```bash
# 1) OpenAPI 规范校验（两个文件都必须通过）
npx --yes @redocly/cli@2.72.1 lint contracts/openapi/g4.yaml
npx --yes @redocly/cli@2.72.1 lint contracts/common/resource-types.yaml

# 2) 跨文件引用可解析（能合并成单文件即证明 $ref 未悬空）
npx --yes @redocly/cli@2.72.1 bundle contracts/openapi/g4.yaml --output /tmp/g4-bundle.yaml

# 3) G4 契约结构自检（零依赖，只需 Node >= 18）
node contracts/local/g4-contract-check.mjs
```

三条命令的退出码均可直接用于流水线判定：非 0 即失败。

`resource-types.yaml` 作为**类型库**被单独 lint 时必然产生 `no-unused-components` 警告
（它没有自己的 paths，组件只被 `g4.yaml` 引用），属预期现象，退出码仍为 0。
因此若 CI 配置了 `--max-problems 0`，只应作用于 `g4.yaml`，不要卡类型库的警告。

**覆盖范围说明**：`g4-contract-check.mjs` 只做结构断言（编号齐全、引用不悬空、
`Ok<T>` 信封、`ResourceChange` 组合、拒绝事实形状、枚举取值、事件样例等 14 项），
