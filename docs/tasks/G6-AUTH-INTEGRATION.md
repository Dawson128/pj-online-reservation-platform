## 实施方案

1. G5-I01 兼容原 `{sessionToken}`；新增实际 `requestMethod` 与可选 `csrfToken`，同一个只读数据库快照验证当前会话、权限及写请求 CSRF。无效会话优先401；CSRF拒绝403并明确字段；服务凭据拒绝与CSRF拒绝可区分。
2. 新增 `shared/auth-client` 纯 Java 库，供预约/维修服务复用；不是新增后端部署单元。G5仍拥有身份事实，消费者只持本次请求的不可变投影，不跨请求正向缓存。
3. 模块以 `ApiAccessRule` 显式声明方法、路径、模块和动作。G6安全链按声明鉴权/CSRF及粗粒度动作检查，未登记路径保持拒绝；对象范围、本人归属、业务回避由对应owner继续检查。
4. 同步开发 Compose 服务凭据、URL及接入说明；HTTP仅用于明确配置的同机开发环境，跨主机使用HTTPS。
5. 传输/安全链测试 + 真正启动G5/预约/维修三个jar并使用隔离PostgreSQL的HTTP验收；测试探针只放测试classpath，不进入产品jar。

## 验收

- 同一真实登录会话可被两个消费者识别；没有cookie、伪造身份头、重复cookie均不能冒充身份。
- 正确写请求成功，缺少/错误/另一会话的CSRF失败；客户端总是传实际方法，原G5内省调用保持可用。
- 退出、账户停用、会话到期或权限版本撤销后，下次请求按G5当前事实拒绝。
- 系统管理员不因身份自动拥有其他业务动作；未登记接口不被放开。
- G5停止、超时、错误服务凭据或畸形响应均失败关闭；不缓存旧身份、不重试未知写请求、不跟随重定向。
- 故意破坏CSRF校验应使真实验收失败，恢复后通过。
