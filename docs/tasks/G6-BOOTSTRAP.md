## 方案与取舍
采用现有三服务/六模块架构；Maven reactor 管三个独立 jar，一个 npm workspace 管前端；按模块分 source/test source，各组只新增自己目录。保留真实网络集成能力，不额外拆六服务。

替代方案：每人新建独立项目再集成，启动快但易产生公共类型、路由、依赖和迁移冲突，未采用。启动包先交付装配与真实边界验证，G6 通知审计另拆任务，避免一次 PR 混入完整业务。

允许修改：G6 公共框架、根构建、启动装配、infra、.github、协作/任务/验证文档，以及其他组已获启动包授权的空目录。保留原业务基线和 skill 原文，不代写 G1—G5 逻辑。

## 验收 oracle 与反例
- 前端能构建，首页明确未开放；不存在的页面有 404 视图。
- HTTP 写操作保留原 key、不自动重试、401 清 CSRF；反例：丢 key 应导致测试失败。
- 三服务能启动，liveness 可查；未知业务、internal 和其他 actuator 被拒绝。删除 denyAll 应导致边界测试失败。
- Docker CI 应启动完整四组件、真实数据库，检查三 schema 隔离和迁移历史；未运行不得记通过。
- 任何业务功能、G5 会话接线、G6 持久通知/审计、完整 readiness、测试服务器部署、生产审批、备份回退均为后续任务。
