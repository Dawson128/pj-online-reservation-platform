# GitHub 团队版本管理与人工冲突处理

把一次协作任务推进到有依据、可复查的完成状态。使用中文说明。给人看的步骤在 [使用说明](使用说明.md)。校园项目的路径和门禁见 [校园项目配置](references/school-profile.md)。

## 0. 校园项目：只声明模块

本仓库是 `git@github.com:Dawson128/pj-online-reservation-platform.git`。当前目录的 remote 已是这个仓库时，不再向用户要链接。

使用者说明自己负责 **G1–G6** 中的哪一个。会话里已经说过则沿用，换模块以最新一次声明为准。没说时只问一句：“你负责哪个模块（G1–G6）？”不要为了开工去登记其余五人的姓名或 GitHub 账号。

声明的模块决定分支前缀 `gN/`、允许修改的目录，以及哪些改动必须请其他模块的人评审。路径表以校园配置为准。用户要求改到别人的目录时，先指出越界，得到该模块的人同意后再改。

## 1. 接入：先确定仓库与任务

1. 本仓库按上一节处理。其他项目仍从用户本次输入取得 **GitHub 仓库 URL**，接受 `https://github.com/OWNER/REPO`、带 `.git` 的 HTTPS 地址、`git@github.com:OWNER/REPO.git` 或等价 SSH URL。GitHub Enterprise 使用用户明确提供的主机。
2. 其他项目缺少 URL 时，先完成可以独立进行的文档/模板工作，再询问：“请提供本次使用的 GitHub 仓库链接。”远程仓库操作等待链接补齐。目录名和历史其他项目不能替代用户输入。
3. 将链接规范化为 `host/owner/repo`，拒绝带令牌、密码或嵌入命令的输入，凭据交给 Git/gh 的认证机制。所有命令参数按 shell 参数安全引用。Git 传输默认 SSH；由用户给出的 HTTPS 链接推导同一仓库的 SSH 地址是协议转换，不是另选仓库。
4. 取得任务类型：初始化协作规则、开始任务、同步分支、提交、创建/更新PR、分析冲突、合并PR、发版、回退、检查状态。范围按用户指令决定；已给出的授权持续有效。
5. 用户希望自己操作时输出可执行命令与前置条件；明确要求代执行时执行授权范围。偏好未知时提供命令。创建本 skill 本身不等于授权操作某个远程仓库。
6. 读取目标仓库的 `AGENTS.md`、适用目录规则、贡献指南、项目配置、需求与技术基线。可用 [配置模板](assets/repository-policy.example.yaml) 建立 `docs/collaboration/repository-policy.yaml`，复用已有等价配置。
7. 记录本次模块、实际主分支、当前分支/HEAD、任务REQ或Issue、允许路径、验收命令与本次允许动作。分支名以 GitHub 默认分支/已批准规则为准，不一律假设 `main`。

仅在校园资源平台任务、项目规则声明使用校园配置，或用户要求按所附任务书执行时，加载校园配置。其他项目读取自己的业务约束；通用核心仍保留人工验收、人工冲突处理和PR质量门禁。

## 2. 操作前检查

按需执行只读检查，输出脱敏摘要：

```bash
git rev-parse --show-toplevel
git status --short --branch
git branch --show-current
git rev-parse HEAD
git diff --stat
git diff --cached --stat
git ls-files -u
git worktree list
```

在内存中检查全部 fetch/push URL、`pushurl` 和 URL 重写后的实际目标，将规范化身份与用户 URL 比较；报告 host/owner/repo，不打印带凭据的原始 remote。仓库不匹配时先定位正确 checkout；保留原 remote，修改目标属于明确的仓库配置任务。

- 工作区已有改动：确认归属；只暂存本任务文件。优先为新任务创建独立 worktree，保留原修改。backup 分支只保存已提交历史，未提交/未跟踪文件另外保留。
- 已有 merge/rebase/cherry-pick/revert 进行中：先识别操作与原始 HEAD，进入对应恢复步骤；恢复目标清楚前保持现场。
- detached HEAD、分支落后或发生分叉：说明事实并选定目标分支。联网同步使用已核对的 remote。
- GitHub 检查用 `gh auth status`、显式 `--repo` 或明确主机的 API；只报告认证是否可用。权限不足时区分“无法读取”与“规则未配置”。
- 空仓库：由管理员完成经过人工验收的最小初始提交、确定默认分支，再启用保护和后续PR流程；在接入记录写明首次建库步骤。其他改动继续按PR交付。

## 3. 新任务与同步

1. 从刷新后的目标分支建立短任务分支，每分支一个可验收改动。未加载校园配置时建议 `feat/<task-id>-<slug>`、`fix/<task-id>-<slug>`、`docs/<task-id>-<slug>`、`chore/<task-id>-<slug>`。校园配置已加载时，分支、路径所有者和评审人以 [校园项目配置](references/school-profile.md) 为准：`gN/<task>`，六人各一个模块。三个部署服务不是三个所有者。
2. 记录基准 SHA 和任务计划：REQ、目的、允许文件、实现方案、验收预期、影响契约/迁移/调用方。校园任务的实现前人工方案检查按校园配置执行。允许路径不得跨进其他模块目录，除非该模块所有者已评审。
3. 并行成员使用不同分支和不同 worktree。同一服务里的两个模块也分开，不得改对方目录。共享接口、公共枚举、迁移编号先登记所有者和依赖；需要前置PR的任务明确其合并次序。
4. 提交前刷新目标分支。共享或已发布任务分支默认将目标分支 merge 进来，保留已有提交历史；选择 rebase 仅限明确采用线性历史的项目策略，且改写范围与协作者已协调。
5. 同步出现冲突时转入 [人工冲突流程](references/conflicts.md)。Git 自动合并无文本冲突也要核验接口、业务规则、配置和迁移之间的语义冲突。
6. 普通推送遇 non-fast-forward 时重新 fetch、检查远端新增提交并协调合并；普通流程采用非强制推送。用户明确要求重写自己独占的任务分支时，先备份并核对远端旧 SHA，再使用绑定期望旧 SHA 的 lease；目标主分支仍通过PR变更。

## 4. 人工验收、提交与PR

使用 [变更记录模板](assets/change-record.md) 保存真实信息。依次完成：

1. 核对需求、契约、实现、调用方、迁移、种子、测试、部署配置和追踪记录是否属于同一变更。
2. 运行仓库实际声明的命令；记录命令、退出码、环境、对应源码 SHA/工作区差异摘要和日志位置。必需命令尚未建立或依赖不可用时，记录“未验证”及具体原因。
3. 展示准确 diff 和测试结果，由真实负责人完成AI产物的提交前人工验收。聊天中已明确对当前差异验收的记录可复用；泛泛的“继续”或创建PR授权不代表已完成行为验收。验收后内容变化，重新检查变化部分。
4. 按文件显式 `git add -- <paths>`，检查 `git diff --cached` 与 `git diff --cached --check`。提交只包含本任务且经过人工验收的变更；保持真实作者，不代签他人验收。
5. 提交格式建议 `<type>(<module>): <task-id> <具体变化>`，正文说明原因、人工验收记录和验证结果。每个真实小批次及时提交，过程证据以真实Git历史为准。
6. 按已核对 remote 推送任务分支。创建或更新PR时显式指定仓库、base/head；正文从文件通过 `--body-file` 传递，使用模板中的真实范围和证据。
7. 未就绪任务可建立 Draft PR，说明剩余工作。Draft不替代提交前人工验收。请求具体人员评审或发布评论等通知行为按用户授权执行；可先准备本地正文。
8. 普通PR至少一位非作者人工评审；跨模块、公共层、数据库迁移按模块所有者逐一核对。同一服务的另一模块所有者不能代替对方验收。评审人必须对当前可审查内容负责，AI检查作为辅助证据。

## 5. GitHub 门禁与合并

初始化仓库协作配置或准备合并时，读取 [GitHub控制规则](references/github-controls.md)。本地文件仅描述规则，服务器回读和实际阻断验证才能证明规则生效。

合并前同时满足：

- 指定仓库、目标分支、PR号和最新 head SHA 与本次任务一致。
- 当前内容已有提交前验收、有效人工PR评审；相关所有者覆盖完整；讨论已处理。
- 实际必需构建/测试/契约/迁移检查通过，结果关联当前候选版本；测试缺失、跳过、取消、超时均按真实执行情况判断。
- PR与最新目标分支组合已验证，使用严格 up-to-date 或可用的 merge queue；队列验证包含 `merge_group`。
- 冲突已由人处理并留下记录，复验通过；分支保护无本次绕过操作。
- 用户本次或会话中已授权合并。若只请求检查或创建PR，交付结果后保持PR原状态。

合并方式优先遵从项目已批准规则。新团队默认建议 **merge commit**，便于保留成员原始提交；采用 squash 时在PR保留细粒度提交与任务证据。使用 rebase merge 时记录重写前后提交映射及评审依据。先核验仓库允许的方法与线性历史设置相容。

执行合并前重新读取 head SHA，使用平台支持的 head 条件检查（如 `gh pr merge --match-head-commit`）。head 变化则重新核验；base 的并发变化交由严格保护或队列重新验证。通过GitHub正常PR入口合并。

合并后回读PR状态、合并 SHA、主分支检查和测试部署状态。明确区分“已合并”“测试环境部署中”“测试环境已验证”“生产待审批”。分支清理限已合并且任务结束的分支；共享分支、其他worktree和未提交修改保留。

## 6. 冲突处理责任

AI负责列出 base/current/incoming、双方目的、REQ差异、影响范围、建议方案和可运行验证命令；**实际冲突编辑与结果选择由人完成**。人工操作后的文件可以由AI复查、按明确授权暂存并运行测试。

冲突现场尚未处理时，先交付完整冲突清单及定位信息再交接。记录为“待人工处理”，同时继续互不依赖的分析。详细步骤、ours/theirs差异、锁文件和迁移冲突见 [人工冲突流程](references/conflicts.md)。

Git未报告冲突但需求或接口两边含义不一致时，同样交给相关所有者确定取舍；修订决定必须同步到契约、需求和验证标准。

## 7. 版本、发布与回退

用 [发布记录模板](assets/release-record.md) 建立不可混淆的对应关系：

`需求/PR → 已合并commit → 统一tag → 制品摘要/契约/迁移 → 测试验证 → 生产审批 → 运行版本`

- 项目已有版本规则优先；初建项目建议 `vMAJOR.MINOR.PATCH`，预发布可用 `-rc.N`。正式tag唯一指向已验证commit，修订通过新版本表达。tag保护/权限在GitHub核验。
- 相同提交构建一次，测试和生产提升同一制品清单；生产使用已有摘要。manifest记录四类信息：源码、制品、契约、数据迁移；以构建/Release资产保存，避免让提交内文件包含其自身最终commit造成循环。
- 测试环境按课程/项目要求自动统一部署；生产操作使用平台人工审批和明确发布授权，普通PR批准不能代替生产审批。
- 部署和使用同一共享环境的集成测试取得同一环境锁，锁覆盖迁移、服务替换、验收和必要恢复。发布临界区采用排队语义，持续运行的迁移不因新提交被随意取消。
- 已执行迁移以新增文件演进。分支迁移冲突先核对各环境执行历史；仅尚未执行的迁移可经所有者确认重新编号，既有校验和保留。
- 应用回退使用旧manifest的制品，核验新schema与旧应用兼容；不兼容时按经演练的数据恢复方案处理。恢复旧备份涉及新业务数据时先制定保留与修复方案。
- 代码撤销通过新的 revert/fix PR，保留公开历史；merge commit 的 revert 先人工确认主线父节点及实际差异。发布回退、代码revert、数据恢复分别记录，三者不互相冒充。
- hotfix 从实际生产tag创建，验证并发布后回合主干及受影响维护分支；重复 cherry-pick 前核对补丁是否已经存在。

## 8. 交付与证据

结尾报告：实际完成动作、仓库/分支/HEAD/PR/tag、实际验证结果、人工验收/冲突处理/评审状态、远程配置是否已回读、发布状态、剩余阻断与下一条可执行动作。

生成的配置有未填值时明确标为模板。校园项目缺少模块声明时先问模块，不因没有六人名单而停。其他项目缺少仓库 URL 时按第 1 节处理。缺少测试命令、规则权限或人工处理证据时，完成其他已授权工作，再说明受影响的具体步骤。引用导致必要人工交接的项目条款和本 skill 的具体段落。

使用 [场景检查清单](references/scenario-checks.md) 检查流程输出。文件/命令创建、测试通过、评审通过、已合并和已上线分别以各自真实证据为准。
