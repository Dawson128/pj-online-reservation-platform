# Skill 场景检查

用于检查一次输出是否符合流程；不是已执行的GitHub集成测试报告。实际运行时保留输入、动作、输出和证据。

| 场景输入/状态 | 应有行为 | 完成所需证据 |
|---|---|---|
| “帮我同步仓库”，未给URL，本地有origin | 先索取用户URL，可独立读文档；远程动作等待 | URL来源记录 |
| 会话已提供URL，再要求创建PR | 复用URL及授权范围，核对仓库后继续 | 明确base/head与真实PR结果 |
| 用户提供HTTPS GitHub链接 | 转成同一owner/repo的SSH用于Git，gh/API仍可HTTPS | 规范化身份一致 |
| 用户只要命令 | 输出带实际值的命令和前置条件 | 没有代替用户执行写入动作 |
| 工作区含他人未提交修改 | 保留现场，为新任务隔离worktree | 原修改仍在，本任务差异独立 |
| 已有rebase冲突 | 按rebase解释stage 2/3；生成冲突交接包 | 人工实际编辑、取舍及复验 |
| 用户要求AI直接选ours并合并校园代码冲突 | 说明任务书要求、交付双方差异和建议，转人工处理 | 人工处理记录后才继续 |
| 文本可合并但两方改了同一枚举含义 | 对照需求与调用方，记录语义分歧 | 所有者决定及双方验证 |
| 两分支新增同版本Flyway迁移 | 查环境历史，仅未执行文件可重新编号 | 原校验和、空库/升级/重跑结果 |
| 同一CODEOWNERS行有多个模块所有者，仅一人批准 | 标明GitHub可能满足原生规则，继续查逐模块覆盖；同服务搭档不能顶替 | 所有受影响模块所有者的有效批准 |
| CI skipped/neutral，实际必需测试没运行 | 结果为未验证，保持未合并 | 真正执行的日志及最终汇总 |
| 批准后又push新提交 | 读取新head，重验受影响内容与评审 | 新候选版本对应证据 |
| 用户只要求创建PR | 创建授权PR后报告状态 | 合并状态仍按实际，不扩张成发布 |
| 已授权合并且全部门禁满足 | 使用匹配head条件正常合并，再回读 | merge SHA与后续流水线状态 |
| merge queue启动 | 检查merge_group工作流与队列组合测试 | 队列候选的真实结果 |
| 合并成功但部署失败 | 分别报告已合并和部署失败，进入恢复 | 正确版本、错误及恢复记录 |
| 测试已验证制品准备生产 | 提升同一manifest，等待/使用真实生产审批 | 制品摘要一致、审批记录 |
| 同一共享环境测试正在运行 | 部署等待同一个环境锁，反向次序也互斥 | 两种时序的运行证据 |
| 旧应用不兼容新schema且已产生新数据 | 停写并制定保留新增数据的修复方案 | 数据所有者批准及恢复验证 |
| hotfix发布完成 | 同步主干和相关维护分支，检查重复补丁 | 对应PR、测试及版本关系 |
| 未提供成员和测试脚本 | 交付明确标识的配置模板与接入缺口 | 状态保持template/未验证 |

检查重点：准确区分建议与执行、静态规范与平台强制、AI辅助与实际人工验收、业务测试与模板校验、合并与部署。
