# 人工冲突处理操作规范

## 责任和完成判据

任务书要求实际代码冲突由人处理。AI可解释、定位、比较、建议和复验；人选择保留的语义并实际编辑冲突文件。AI直接写入解决结果再让人点确认，不作为校园项目的人工处理证据。

已取得普通合并授权且同步遇冲突时，先完成只读分析和交接包。处理者提交已编辑文件或说明具体处理完成后，AI读取实际差异并验证。人工记录至少包含：处理者、发生时间、操作类型、双方SHA、文件、双方意图、最终取舍、对应需求、复验结果。

## 1. 识别现场

以下是检查命令，执行前定位正确仓库：

```bash
git status
git ls-files -u
git diff --name-only --diff-filter=U
git diff --cc
git reflog -n 12
```

`git status`区分 merge、rebase、cherry-pick、revert。保留操作开始前的分支名、HEAD与已核对的目标SHA。检查是否为本任务创建的现场。

按需读取单个冲突文件的三方内容，`path/to/file`替换为实际路径：

```bash
git show ':1:path/to/file'
git show ':2:path/to/file'
git show ':3:path/to/file'
```

stage 1是共同基线，stage 2是当前操作的ours，stage 3是theirs。新增/删除/重命名冲突可能缺某个stage，按 `git ls-files -u` 和重命名信息解释，不将“缺失”当作空文件。

普通 merge：ours为当前检出的分支，theirs为合入分支。rebase：ours通常是正在重放到的目标历史，theirs通常是正在重放的原分支提交，与直觉上的“我的分支”不同。cherry-pick/revert同样按当前操作解释。先用SHA和内容识别两边，再讨论取舍。

## 2. 输出可操作交接包

对每个文件输出：

| 项 | 应填写的真实信息 |
|---|---|
 位置 | 文件路径、冲突块或函数、所属组 |
 三方 | base/current/incoming的SHA及内容摘要 |
 意图 | 双方分别在解决什么问题，对应哪个REQ/PR |
 冲突 | 同一字段/状态/接口/迁移的分歧，保留任一方会失去什么 |
 建议 | 根据已批准需求说明可选处理方式和影响，最终由所有者决定 |
 验证 | 人工编辑后需要运行的实际命令及可观察预期 |

工作区有未提交改动时，隔离分析优先使用临时worktree。保留冲突文件以及未跟踪资产；备份分支不能替代这些文件的备份。

## 3. 人实际处理文件

在交接中指出准确操作目录，由人使用编辑器逐块处理：

- 普通源码：合并双方仍有效的功能，按当前需求取舍冲突内容。
- 接口和DTO：提供方与调用方共同确认字段、枚举、错误及版本，更新双方实现和测试。
- 需求/技术/ADR：记录批准的决定，再同步实现；文档先后时间不自动决定正确性。
- 依赖清单和锁文件：人先确定依赖清单，由同一锁定工具版本重建锁文件，复查依赖差异并执行可重复安装。工具重建发生在人工取舍之后。
- 已发布迁移：核对各环境历史和校验和，保留已执行文件，新增修复迁移；尚未应用的同号迁移由所有者重新编号后验证空库、升级与重跑。校园项目按 [校园项目配置](school-profile.md)：版本键含组号 1–6，未发布分支要重编到主干该 schema 最大版本之后，禁止 outOfOrder；m1/m2/m3 各只有一套 Flyway 历史。
- 二进制：用可读取工具比较内容，由资产所有者提供确认版本或从源文件重新生成。
- 删除/修改和重命名：确认最终路径、引用、导入、部署脚本与测试一起更新。

## 4. 复验与继续

人编辑完成后，AI按授权读取文件、核对三方需求，并运行已有验收命令。以下命令中的实际文件由逐项核对后填入：

```bash
git diff --check
git diff -- path/to/resolved-file
git add -- path/to/resolved-file
git ls-files -u
git diff --cached --check
git diff --cached
```

扫描改动文件中的冲突标记，并区分文档示例与残留标记；`git ls-files -u`为空仅说明索引没有未解决项，不能证明语义正确。

验收后，根据 `git status` 确认的操作只执行对应命令：

| 进行中的操作 | 本轮已验收后的继续命令 | 放弃本轮的恢复命令 |
|---|---|---|
 merge | `git merge --continue` | `git merge --abort` |
 rebase | `git rebase --continue` | `git rebase --abort` |
 cherry-pick | `git cherry-pick --continue` | `git cherry-pick --abort` |
 revert | `git revert --continue` | `git revert --abort` |

继续后可能遇到下一提交的冲突，按同一流程再次处理。空提交是否跳过由任务内容与补丁是否已存在决定。放弃操作会丢掉本轮人工解决结果时先保留文件，并按用户恢复意图执行；abort失败则检查现场，保留修改后再制定恢复方式。

最终对完整候选版本运行相关测试，重新记录SHA和差异。推送后等待最新CI与有效人工评审，再通过PR合并。过去版本的绿灯不代表当前人工解决后的版本已通过。

## 5. 无文本冲突的语义检查

至少核对：同名枚举取值、接口可选/必填、状态转换条件、权限范围、时间边界、事件去重键、迁移顺序、依赖锁版本、前后端序列化、测试预期是否被同时改错。发现基线分歧时记录文件与REQ，请所有者作出实际决定。
