# Git 工程协作 skill 使用说明

给六名模块负责人用。仓库已经固定，开口说明自己是哪个模块，再说要做的事。

仓库：`git@github.com:Dawson128/pj-online-reservation-platform.git`

技能目录：`github-team-workflow/`。Agent 按 `SKILL.md` 执行；路径和门禁在 `references/school-profile.md`。

## 这个 skill 做什么

它管的是 GitHub 上的协作过程，不代替写业务代码，也不做泛泛的代码评审。

| 你说的事 | 它做的事 | 它不做的事 |
|---|---|---|
| 开始做某项需求 | 从最新主干拉分支 `gN/<task>`，写明允许改的目录、方案和验收标准 | 未经过你看方案就改别人的模块 |
| 同步主干 | 把目标分支合进你的任务分支，列出冲突 | 自己选定冲突两边并合并 |
| 提交 | 只暂存你的模块路径，写带模块名的提交说明，推送 | 把未验收的 AI 改动直接提交；不代签别人的名字 |
| 开或更新 PR | 写清范围、验证结果和要请谁看，创建或更新 PR | 把“创建 PR”当成已经允许合并 |
| 看冲突 | 列出双方改了什么、对应哪条需求、建议和验证命令 | 按课程要求，冲突内容必须由人改完 |
| 合并 PR | 核对评审、检查和 head SHA 后，从 PR 入口合并 | 绕过保护规则强推主干 |
| 发版 | 记录四个组件同一套 tag、镜像摘要和三个 schema 版本 | 用普通 PR 批准代替生产人工审批 |
| 回退 | 分开记录应用回退、代码 revert、数据恢复 | 把三者说成同一件事 |
| 看状态 | 报告分支、PR、检查、冲突和还缺的人工步骤 | 把没跑的测试写成通过 |

提交前你要自己看过 diff 和行为。冲突文件要你自己改。生产发布要另外的人批。

## 怎么开口

先说模块，再说动作。同一段对话里说过模块，后面可以不重复；换模块时重新说。

```text
我是 G1。给需求 3.2 提交预约开一个分支，只改我的目录。
```

```text
我是 G4。把主干同步到当前分支，有冲突就列出清单，先别改文件。
```

```text
我是 G6。这个 PR 的检查已经绿了，帮我核对能不能合并。先不要合并。
```

没说模块时，Agent 只会问你是 G1 到 G6 的哪一个，不会让你先填六个人的名单。

## 六个模块能改哪里

同服务的另一个人不是你的共同所有者，也不能替你验收。

| 你说 | 职责 | 服务 | 分支前缀 | 主要目录 |
|---|---|---|---|---|
| 我是 G1 | 个人预约、签到、申诉、统计 | reservation | `g1/` | `features/g1`、`modules/g1`、`db/m1/g1`、契约 `g1` |
| 我是 G2 | 整室申请和两级审批 | approval | `g2/` | `features/g2`、`modules/g2`、`db/m2/g2`、契约 `g2` |
| 我是 G3 | 报修、派改、验收、评价 | maintenance | `g3/` | `features/g3`、`modules/g3`、`db/m3/g3`、契约 `g3` |
| 我是 G4 | 房间座位、占用台账、资源事务协调器 | reservation | `g4/` | `features/g4`、`modules/g4`、`integration/`、`db/m1/g4`、契约 `g4`、公共资源类型 |
| 我是 G5 | 账户、角色、权限、院系、业务参数 | approval | `g5/` | `features/g5`、`modules/g5`、`db/m2/g5`、契约 `g5`、公共身份类型 |
| 我是 G6 | 通知、审计、前端公共框架、构建和发布 | maintenance | `g6/` | `features/g6`、`modules/g6`、`db/m3/g6`、契约 `g6`、前端 Shell、`shared/ui`、`infra`、各服务启动装配 |

前端路径在 `apps/web/src/` 下，后端模块在 `services/<服务>/modules/` 下。各组只导出自己的 `routes.ts` 和 `navigation.ts`，由 G6 注册。完整表见 `references/school-profile.md`。

改公共类型、锁顺序、跨模块状态或数据库 schema 时，提供模块和每个使用模块的人都要看。G6 不替其余五个人写测试。

## 一次正常开发

1. `我是 G2。开始做需求 4.2 一级审批。`
2. 看 Agent 给出的方案和允许目录，同意后再让它改代码。
3. 自己点过页面或看过测试输出，然后说：`我看过当前 diff，可以提交。`
4. `推上去并开 PR，请 G5 看权限契约。先不要合并。`
5. 别人评审、检查通过之后，再单独说：`可以合并这个 PR。`

“继续”“开 PR”都不等于你已经验收过行为，也不等于允许合并。

## 遇到冲突

你自己在编辑器里改冲突文件。改完告诉 Agent 你改好了，它再跑检查、暂存并继续合并或变基。

不要说“你帮我选一边直接合并”。课程要求冲突由人处理。

## 发布和回退

测试环境在合入后部署全部四个组件：web、reservation、approval、maintenance。不能只部署自己的模块。

生产发布只由被明确授权的人发起，并指向具体的 tag 和 manifest。回退时说明是退应用、撤回代码，还是恢复数据。
