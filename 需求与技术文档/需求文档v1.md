# 校园资源服务平台需求文档

文档版本：需求基线 v1.3（2026-10-16）。本文件规定待建设系统的业务行为和工程交付标准，不代表功能已经实现、测试通过或已经完成全组会签。技术方案、接口及实现映射见[技术文档](技术文档.md#tech-overview)。实际成员姓名、评审日期和执行证据由项目组在实施时填写；核心规则按本基线执行，变更必须留痕。

## 1. 目标、来源与分工

建设统一 Web 校园资源服务平台：以个人自习座位预约为核心，连接整教室申请审批与物业报修；学生能发现和使用可用资源，管理人员能依据预约、故障和违约记录管理空间。学生页面适配手机浏览器，管理页面支持桌面浏览器。工程交付包含三个业务模块、公共能力、集成验证、流水线和真实过程证据。

来源为同目录《任务书.pdf》。下文“原文要求”指原文直接规定；“项目补充设计”指为落实原文而自行确定的规则。混合条目标明两者，不能将细化参数、状态或技术选择当作课程原文。

## 2. 全局业务规则与状态

以下时间均使用 Asia/Shanghai，所有时间区间为左闭右开 `[开始,结束)`；相邻时段不冲突。用户端与服务端时间不一致时以服务端时间为准。调度周期不超过60秒；截止规则按应生效时刻判断，执行和通知可在随后60秒内完成，不能因调度延迟多获得合法签到时间。

| 事项 | 本基线默认值与边界 |
| --- | --- |
| M1预约 | 开始和结束均为整点；每次1—4小时；单次上限可配置为1—8小时；开始必须晚于当前时刻且不超过未来7天；同人同时仅一个有效个人预约 |
| M1签到 | 可签到区间 `[开始前15分钟,开始后15分钟)`；开始后15分钟整尚未签到即违约；结束时自动完成 |
| M1提醒 | 开始前15分钟、开始后10分钟未签到、开始后15分钟未签到取消；预约创建晚于首次提醒时刻不补发该次提醒 |
| M2申请 | 提前至少1小时、最多14天；整点小时，单次1—8小时；固定两级审批；总审批截止为 `min(提交后24小时,预约开始)`，一级通过不重置截止；有效批准时刻取M1完成最终资格/冲突裁决所记录的服务端时刻，须该原子裁决最终持久化成功；持久化完成和响应可晚于截止，失败回滚则无批准事实 |
| M3时限 | 提交后4小时仍未派单升级；开始维修后24小时仍未验收升级；从开始维修到验收通过保持封锁，无预估结束时间自动释放 |
| 评价 | 验收通过后7天内，上报人可提交一次1—5整数分及可选、不超过500字的评价 |

可预约的必要条件是：空间与座位有效、满足院系访问范围、覆盖完整开放时段、管理员停用区间不冲突，且没有有效 M1个人占用、M2整室占用或M3维修限制。不同限制叠加，删除某条限制不能覆盖其他限制。M3维修影响整室全部座位，并阻止未结束时间范围内的新预约，直到对应工单验收释放。主数据注销采用保留历史的停用方式；发生有效记录冲突时按维护影响规则处理，不能直接删除历史。

| 对象 | 正常路径及终止分支 |
| --- | --- |
| M1预约 | 已预约→已签到→已完成；已预约→用户取消/未签到取消/系统取消；已签到→系统取消。终态不再占用；系统取消包含维护原因 |
| M2申请 | 待一级→待二级→占用处理中→已批准→已结束；待审批可驳回、申请人撤销或超时撤销；最终占用失败为资源冲突；已批准可撤销或由维护触发系统取消 |
| M3工单 | 已提交→已派单→维修中→待验收→已验收；验收不通过回维修中；派单前本人可取消，已派单且未开始维修可由管理员说明原因关闭；维修中/待验收不能直接关闭 |

M2待审批不预先锁座，多条申请可以重叠；第二级通过必须成功取得整室占用才算已批准。原文“驳回/超时回滚”在本方案中解释为撤销本申请产生的预占或处理残留；正常待审批无占用时为空操作，仍须保证不误释放其他来源。M3原文“验收通过自动恢复”解释为移除本工单限制后重新计算可用性；仍有其他工单、停用或预约时不恢复可预约。

维护事件包括 M3开始维修、管理员停用、注销及开放时间缩短造成的有效记录冲突：对未结束的M1整条系统取消，对已批准且未结束的M2整条系统取消，保留历史、释放各自占用、通知相关人；不做部分截断或自动改签。M1不因维护新增违约；但未签到截止早于或等于维护生效时刻的，先按应生效截止结算未签到取消和违约，即使扫描尚未执行也不豁免。仅维护早于未签到截止时豁免，若之后误记则冲正；维护前已成立的违约和已完成记录不追溯删除。恢复后原记录不自动复活，用户重新申请。

## 3. M1个人座位预约需求

<a id="req-m1-001"></a>
### REQ-M1-001 可用空间查询
来源：原文要求 S8；访问过滤与展示字段为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：学生按日期和时段查看校级开放空间及本院系空间，展示空间名、地点、开放时间、可预约座位数、院系范围和不可用原因，不以静态座位总数代替可用数。
验收 AC-M1-001：前置：同一时段有校级房间、本院系房间、外院系房间及维修房间；操作：学生查询；预期：前两者可按剩余量进入，外院系无预约入口，维修房间标为维修不可用且可用数为0；直接请求外院系预约也被拒绝。

<a id="req-m1-002"></a>
### REQ-M1-002 条件搜索与插座标记
来源：原文要求 S8；组合条件为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：支持日期/时段、区域、空间、座位编号和插座条件组合搜索；固定插座、移动导轨插座、无插座分别标记；同一查询采用全局可用性规则。
验收 AC-M1-002：前置：三类座位各有一个，另有带插座但被占用的座位；操作：筛选指定时段和“固定或移动插座”；预期：只返回满足时段且有对应标记的可用座位；取消条件后可见无插座座位，结果不会混入被占用座位。

<a id="req-m1-003"></a>
### REQ-M1-003 整点时段与可调时长
来源：原文要求 S8（整点小时、默认最多4小时、上限可调）；提前窗口为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：按第2节检查时段；上限变更仅作用于新申请，既有合法预约保留，变更记录参数版本。
验收 AC-M1-003：前置：默认上限4小时且房间开放；操作：分别提交1小时、4小时、5小时、10:30开始、零时长及过去时段，再将上限改为5并提交5小时；预期：仅前两项及变更后的5小时成功，其他项给出具体校验原因，旧预约不因参数变更失效。

<a id="req-m1-004"></a>
### REQ-M1-004 预约确认与冲突保护
来源：原文要求 S8；并发和同人限制为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：创建时重新检查身份、范围、完整开放时段及全部有效限制；同座位重叠、同人重叠不得重复成功；页面搜索结果不构成占用承诺，重复提交同一次业务操作不得创建多个预约。
验收 AC-M1-004：前置：同室S1/S2在未来合法时段均空闲，A/B无重叠预约；操作：分别用独立重置的夹具构造A先成功、B先成功两种并发交错，记录抢S1成功者为W、败者为L，重放W成功请求；再由W申请空闲S2重叠时段，被拒后由L申请该时段；另用重置夹具让W先预约S1，再申请S2且开始恰等于前一预约结束；预期：每种交错首轮均仅一人成功、S1占用和记录各一条，重放返回原结果；W重叠拒绝，L在空闲S2合法成功；隔离的相邻区间申请成功，不受前一分支新占用干扰。

<a id="req-m1-005"></a>
### REQ-M1-005 本人取消预约
来源：项目补充设计，支持 S8预约周转。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：本人可在开始前取消“已预约”记录，不产生违约；开始后及已签到不允许本人取消，管理员不得借取消任意擦除违约。取消释放该预约占用并保留原因和时间。
验收 AC-M1-005：前置：A有未来预约，B无该记录权限；操作：B取消、A取消并重复取消，再尝试取消已开始预约；预期：B拒绝，A未来预约变用户取消且座位恢复按其他限制计算，重试不多释放；已开始预约拒绝。

<a id="req-m1-006"></a>
### REQ-M1-006 每日教室签到编码
来源：原文要求 S8（每日动态、教室关联、Web输入编码）；具体有效期为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：每室每日0点生成当日随机编码，同日不同室不共用；仅授权教室显示屏页面及管理人员可读取完整编码，普通学生查询接口不能返回编码；编码须对应房间，按实际签到日期校验当日有效码，不按预约开始日期校验；00:00开始预约可在前一天23:45起用前一天当前有效码，跨0点后须用新码。
验收 AC-M1-006：前置：两个房间及前后两天的编码；操作：授权屏幕读取，普通学生请求编码，用昨日或他室编码签到；预期：屏幕显示当日对应码，学生读取被拒，旧码与他室码均不能完成签到；对00:00预约，23:45当前有效码能签到，0点后旧码失效且新码能签到。

<a id="req-m1-007"></a>
### REQ-M1-007 预约签到与边界
来源：原文要求 S8；提前签到窗口为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：仅本人以正确房间当日码在第2节签到区间内对有效预约签到；成功后不再触发未签到提醒和违约。重复签到返回原成功结果；预约已因维修取消时即便编码正确也不成功。
验收 AC-M1-007：前置：09:00预约与正确编码；操作：分别在08:44:59、08:45、09:14:59、09:15测试独立预约，另测试他人、错误码及系统取消记录；预期：仅区间内本人有效记录签到成功，09:15整不能因取消任务尚未执行而成功；重复请求不改变签到时间。

<a id="req-m1-008"></a>
### REQ-M1-008 开始前提醒
来源：原文要求 S8；去重和迟创建处理为项目补充设计。责任组：第一组主责，第三组通知。映射：[M1](技术文档.md#tech-m1)。
规则：开始前15分钟向仍有效且未签到的预约人发送真实邮件，含空间、座位、起止时间与签到入口；事件不得重复发送，晚创建不补发已过去的这一提醒。
验收 AC-M1-008：前置：09:00有效预约、已取消预约、08:50才创建的09:00预约；操作：推进至08:45并重跑任务；预期：60秒内第一条邮件到测试收件箱且含正确内容，取消记录无邮件，重复任务无重复邮件，迟创建不补发08:45事件。

<a id="req-m1-009"></a>
### REQ-M1-009 开始后未签到提醒
来源：原文要求 S8（开始后10分钟未签到提醒）；发送前再核验与重复任务去重为项目补充设计。责任组：第一组主责，第三组通知。映射：[M1](技术文档.md#tech-m1)。
规则：开始后10分钟仍有效且未签到时再次邮件提醒，明确还有5分钟截止；发送前再次核验，已签到或已取消不发送。
验收 AC-M1-009：前置：两条09:00预约，其中一条09:09已签到；操作：推进至09:10并重跑；预期：仅未签到者在60秒内收到一次邮件，已签到者无迟到提醒，内容截止时间为09:15。

<a id="req-m1-010"></a>
### REQ-M1-010 未签到取消、释放与违约
来源：原文要求 S8（15分钟取消、释放、提醒及违约）；单预约违约唯一、邮件失败隔离与维护豁免为项目补充设计。责任组：第一组主责，第三组通知。映射：[M1](技术文档.md#tech-m1)。
规则：开始后15分钟仍未签到则自动取消、释放本预约占用、向本人发邮件、后台记一次违约；同一次预约最多一条有效违约。邮件失败不阻止取消，维护豁免按 REQ-M1-014 执行。
验收 AC-M1-010：前置：09:00—11:00未签到预约；操作：推进09:15、重复截止任务并模拟邮件暂时失败；预期：60秒内变未签到取消且释放占用，一条违约，邮件恢复后补送一次取消通知；09:15以后不能签到，其他来源限制不被删除。

<a id="req-m1-011"></a>
### REQ-M1-011 历史查询与再次预约
来源：原文要求 S8；历史字段为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。
规则：本人按日期、空间和状态查历史，展示原时间、签到/取消原因及关联违约；“再次预约”带出原座位，用户选择新时段后按全部新规则提交，不能复制旧占用或绕过停用。
验收 AC-M1-011：前置：一条已完成记录及一条已停用座位历史；操作：查看本人/他人历史，分别复用到新空闲时段；预期：仅本人可见其历史，空闲有效座位创建新编号预约，停用座位明确拒绝并保留旧记录。

<a id="req-m1-012"></a>
### REQ-M1-012 运营预约与利用情况
来源：原文要求 S8；指标口径为项目补充设计。责任组：第一组。映射：[M1](技术文档.md#tech-m1)。

### REQ-ENG-012 脚本化环境与部署互斥

规则：基础设施、启动、检查和清理由版本化脚本/容器配置支撑；项目级部署窗口采用互斥机制覆盖全组发布与集成测试，运行中的测试不得与迁移或发布交错。配置分环境，凭据通过受控环境配置提供，避免依赖个人手工服务器操作。
验收 AC-ENG-012：前置：干净环境及一条运行中集成测试；操作：脚本建立环境，同时发起发布和集成测试；预期：一方等待或明确拒绝，未出现部署中的误报失败；环境可重复建立，第三方成员按文档可完成运行检查。

<a id="req-eng-013"></a>
### REQ-ENG-013 需求实现验证追踪与缺口
来源：原文要求 S5。责任组：各组维护，第一组验收汇总。映射：[追踪](技术文档.md#tech-traceability)。
规则：以本文件需求ID关联技术章节、任务、实际代码/接口/迁移、测试/AC和交付状态。当前均为待实现；实施中记录未完成、失败、延期及原因，不能从清单移除。需求变更评审后更新基线版本、影响和追踪关系。
验收 AC-ENG-013：前置：当前基线及一个已实现/一个未完成迭代条目；操作：抽查链路并改动一项需求；预期：可从任一需求定位实现和证据，未完成明确存在且无伪造通过；变更有前后记录、评审与相关测试更新。

<a id="req-eng-014"></a>
### REQ-ENG-014 测试行为与故障注入验证
来源：原文要求 S5（真实行为测试及故意破坏实现验证）；四类指定变异、独立约束测试与失败恢复证据细则为项目补充设计。责任组：各组，第一组牵头集成。映射：[验证](技术文档.md#tech-verification)。
规则：测试使用固定前置和预先定义预期，实际调用被测逻辑，禁止断言常量、只覆盖空分支或mock掉核心逻辑。至少对权限、冲突占用、未签到截止、多工单来源释放各故意破坏实现一次，证明确切测试失败，再恢复并复跑；记录破坏点、失败断言和版本。变异须实际改变对应行为；不能要求业务用例必然检测移除冗余保护。违约唯一约束另以真实数据库重复插入测试验证拒绝第二条记录。
验收 AC-ENG-014：前置：四项行为测试原先通过；操作：逐项移除权限检查、放行冲突、禁用违约生成、改成释放全室所有限制；另直接向真实数据库插入同预约的第二条违约，随后在隔离测试库临时移除唯一约束复验；预期：四项业务测试分别因越权成功/重复占用/缺少违约/误释放其他来源失败，恢复后通过；数据库约束测试在约束存在时拒绝重复写入，移除后因错误允许重复而失败，恢复后通过。若另禁用截止转换，则由未取消/未释放断言检测；不能以增加无关常量断言制造失败，也不要求仍有行锁/状态机保护的重复调度用例必然检测移除唯一约束。

### REQ-ENG-015 评审节点与实际展示
来源：原文要求 S7。责任组：第二组统筹，各组准备，第一组核验链路，第三组运行。映射：[验证](技术文档.md#tech-verification)。
规则：项目组自行排期并持续可查。启动交分工/公共层决策；第一次Review交需求基线、任务依赖、架构与首迭代、规则/AI协作和风险；第二次交主功能/集成、自动迁移与提交到部署、质量保证；期末交完整功能及过程说明。实际演示全新环境流水线部署、提交触发构建测试、一次schema演化、生产审批发布和回退、通过网络完成的跨模块状态写回，不用截图代替操作。
验收 AC-ENG-015：前置：真实节点材料及可操作环境；操作：逐项核对并现场执行五项工程演示；预期：材料对应实际版本，操作可看到构建/测试/迁移/发布/回退和源状态变化，日志可追溯，失败记为未完成并补验，人员和日期仅填真实情况。

## 9. 工程伦理与非功能需求

<a id="req-eth-001"></a>
### REQ-ETH-001 最少数据与访问控制
来源：原文要求 S6；具体保护为项目补充设计。责任组：第二组身份权限，各组落实本域，第三组审计。映射：[伦理](技术文档.md#tech-ethics)。
规则：只采集校内身份、院系、联系邮箱及业务必要内容；不收集精确定位、生物识别或无关敏感资料。学生只见本人明细，管理员按职责/空间访问，维修人员只见执行工单必要联系信息；报修描述提示勿填敏感信息，日志和测试材料脱敏。
验收 AC-ETH-001：前置：两个学生及范围不同的管理员；操作：互读历史、越界查报修/统计、检查采集字段与日志；预期：越权均拒绝，无额外敏感采集，正常业务可完成，日志不暴露密码/完整签到码/不必要个人描述。

<a id="req-eth-002"></a>
### REQ-ETH-002 公平规则与限制解释
来源：原文要求 S6；具体公平措施为项目补充设计。责任组：第一组主责，第二、三组各管本域。映射：[伦理](技术文档.md#tech-ethics)。
规则：展示预约时长、院系限制、截止/违约、审批与维修规则；同权限同条件按相同规则，不为管理员或整室申请自动挤占已成功个人预约。不可用结果说明类别，统计明确口径；每日编码只能作为签到凭证，不声称证明实际物理在座。
验收 AC-ETH-002：前置：两个同权限用户、受保护个人预约和院系限制室；操作：同条件申请、审批整室、查看规则与失败提示；预期：一致执行，个人预约不被审批挤掉，失败可解释，展示未将签到数据夸大为实际在座事实。

<a id="req-eth-003"></a>
### REQ-ETH-003 违约查询、申诉与纠错
来源：原文要求 S6、S8（违约）；申诉为项目补充设计。责任组：第一组主责，运营管理员人工处理，第三组审计。映射：[伦理](技术文档.md#tech-ethics)。
规则：本人可见违约预约、应截止时刻和依据，提交一次文字申诉（1—1000字），授权运营管理员据日志人工确认保留或冲正并给理由。冲正保留原记录与审计，不改变原始时间；本期不设自动封禁或信用惩罚。
验收 AC-ETH-003：前置：合法违约与维护误记各一条；操作：本人申诉、他人申诉、管理员结合维护生效记录处理；预期：本人合法提交，他人拒绝；合法违约保留有理由，误记冲正并通知本人，原证据可查且没有自动封禁。

<a id="req-eth-004"></a>
### REQ-ETH-004 证据真实性与人的责任
来源：原文要求 S3、S6。责任组：各组。映射：[伦理](技术文档.md#tech-ethics)。
规则：明确AI辅助的任务范围、人负责审阅/验收/发布，记录事实、推断、待验证项；不得伪造组内一致、测试结果、用户数据或部署状态。缺陷、限制和失败须进入问题记录与需求状态，不以AI生成说明作为证明。
验收 AC-ETH-004：前置：一次真实开发和一次失败测试；操作：核对说明、提交、测试/发布日志与人工责任记录；预期：陈述均有对应证据，失败未被标通过，无证据项标待验证，AI与人的贡献和责任可区分。

<a id="req-eth-005"></a>
### REQ-ETH-005 过程伦理记录与个人论文
来源：原文要求 S6。责任组：各成员记录本人工作，各组汇总过程问题。映射：[伦理](技术文档.md#tech-ethics)。
规则：在需求、设计、实现、测试、部署阶段持续记录实际遇到的隐私、公平、资源冲突、AI质量和责任问题，包含情境、备选应对、决策、剩余疑问和证据；每位成员在个人课程论文中结合本人参与分析，不以期末补造案例替代。
验收 AC-ETH-005：前置：至少两个阶段真实问题记录和本人参与证据；操作：抽查个人论文与问题链路；预期：能定位本人工作、真实问题、处理与未解点，内容与过程事实一致，人员姓名和讨论结果真实填写。

<a id="req-eth-006"></a>
### REQ-ETH-006 安全运维、保留与删除
来源：原文要求 S6；保留策略为项目补充设计。责任组：第三组运行与审计、第二组账户，各组数据所有者。映射：[伦理](技术文档.md#tech-ethics)。
规则：生产凭据仅授权维护人员可取，用传输保护与受控备份；备份每日一次、保留7天，至少演练一次恢复。课程部署期间业务记录和审计保留至课程结束后90天，届时经授权执行删除或不可逆匿名化并保留不含身份的汇总；删除须清理到期备份，不能由普通用户直接擦除审计，真实用户数据不进入公共演示或公开仓库。
验收 AC-ETH-006：前置：含测试用户记录的受控环境、备份和到期样本；操作：验证非授权备份访问、恢复演练、执行到期清理，核查含清理前一天仍在7天保留期内的旧备份，并检查演示材料；预期：越权拒绝、到期前恢复演练可核对记录一致，到期清理后包括上述旧备份在内均不能恢复到期身份，清理结果可审计，公开材料无真实用户个人信息。

## 10. 基线使用与交付判定

以上71条需求构成完整验收清单。AC编号与需求编号一一对应；技术文档负责进一步指定接口、数据、实现位置与测试方法，实际代码位置在实现时补入追踪表。验收使用本条前置、操作、预期作为固定判据，多场景条目必须全部满足，不能只选正常路径。所有需求当前状态为“待实现”；只有在实际人工核验和证据齐备后才可更新为通过。

项目进度以任务依赖、评审节点及真实完成状态维护，不设虚构统一日期。开始实施时优先验证 M1占用与截止、M2最终占用确认、M3多来源限制及两条写回链路，再扩展完整页面和运营展示。任何简化必须通过需求变更，不能删除原文M1、工程交付或伦理要求。
