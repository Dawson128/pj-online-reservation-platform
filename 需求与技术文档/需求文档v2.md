# 校园资源服务平台需求文档

需求基线 v1.4（2026-10-23）。本文件说明系统提供什么功能、用户如何使用，以及各项业务应遵守的规则。它规定待建设系统的预期行为，不表示功能已经完成。

## 1. 系统概述

### 1.1 建设目标

建设统一的校园资源服务平台，帮助学生找到并使用可用自习座位，帮助有权限的校内用户申请整间教室，并让故障上报、维修和恢复开放形成完整流程。管理人员能够根据预约、故障和违约记录管理空间，用户能够查明申请结果和资源不可用的原因。

### 1.2 三项主要服务

- **自习座位预约**：查询和搜索座位，选择时段预约，按要求签到，取消预约，查询历史和违约、提交申诉。
- **整教室预约审批**：有权限的申请人提交整室用途和时段，由教室管理员、运营管理员依次审批，批准后占用整间教室。
- **物业报修维修**：用户上报故障，教室管理员派单，维修人员处理，管理员验收，用户评价；维修期间同步限制该教室的预约。

三项服务共用账户、空间、座位和业务记录。个人预约、整室占用、维修及管理员停用共同决定资源是否可用；任一页面都应遵守同一判断结果。

### 1.3 整体使用形态与范围

平台通过浏览器使用。学生可以在手机上完成搜索、预约、取消、输入签到编码和查历史；管理人员可以在电脑上处理审批、维修、空间配置和统计。空间包括普通教室、图书馆及其他登记的学习空间，可以面向全校开放，也可以仅向指定院系开放。

本期支持文字报修，不依赖附件；不设置自动封禁或信用惩罚。签到编码用于完成签到，不能证明用户实际身处座位，也不用于测量真实在座时长。

### 1.4 时间与结果的共同约定

所有时间使用北京时间（Asia/Shanghai），以系统当前时间为准。一个时段包含开始时刻、不包含结束时刻：例如09:00—10:00与10:00—11:00互不重叠。

到期、提醒和升级等自动处理的检查间隔不超过60秒；应在相应时点之后60秒内完成状态处理；邮件正常可用时，对应提醒或升级邮件也应在这60秒内送达。通知故障时按第8.2节重试，不延后应生效的业务结果。是否逾期按规则规定的时点判断，不能因为页面尚未刷新或自动任务稍后执行而延长签到、审批或撤销的期限。

## 2. 用户角色与权限

### 2.1 六类业务角色

| 角色 | 可以使用的功能与对象范围 |
| --- | --- |
| 学生 | 查询全校开放或本院系空间，预约个人座位，查看本人预约、违约和申诉，上报有权访问空间的故障并评价本人报修 |
| 整室申请人 | 获得整室申请权限的校内账户；在可访问空间提交整室申请，查询和撤销本人申请 |
| 教室管理员 | 管理授权空间和座位、开放时间，进行一级审批，派单、改派、验收维修，查看授权教室签到屏幕 |
| 运营管理员 | 在授权范围进行二级审批、终止已批准整室申请，查看运营统计、处理工单升级和违约申诉 |
| 维修人员 | 查看本人被派工单的必要信息，开始维修，记录进度和提交完工 |
| 系统管理员 | 维护账户、角色、动作权限、管理范围及系统参数；办理预约、审批、维修等业务仍须具有相应业务权限 |

### 2.2 每次操作都检查权限和对象范围

能进入某个页面，不代表可以操作其中所有记录。系统应同时核对账户是否有效、是否有该操作权限，以及是否满足房间管理范围、院系范围或本人记录归属。直接提交操作、查看详情和重试失败操作也适用这些规则。

学生只能看到本人预约、违约和申诉的明细；其他学生的身份、预约用途和联系方式不对其公开。教室及运营管理员只能处理授权空间的记录。维修人员只能看到执行本人被派工单所必需的联系信息，不能借维修权限浏览其他用户资料。

<a id="req-d-002"></a>
### 2.3 多角色、授权与业务回避

同一账户可以有多个角色。系统管理员可以新增角色，把已登记的操作权限与空间范围组合授予或撤销，保留内置的教室管理员和运营管理员角色。新增角色通过配置生效；例如“区域查看员”可以只读指定教室统计，不能写入数据或查看其他教室。撤销后，新的操作立即按撤销后的权限检查，授权前后配置保留记录。

角色叠加不能绕过业务回避：两级审批人均不得审批本人申请；一级和二级不能由同一人完成，即使此人兼任两种管理员。维修人员不能验收本人维修的工单。账户具备系统管理权限，也不能自动获得以上业务权限。

## 3. 自习座位预约

<a id="req-m1-001"></a>
<a id="req-m1-002"></a>
### 3.1 浏览空间与搜索座位

学生选择日期和时段后，可以查看全校开放空间及本院系空间。每个空间显示名称、地点、开放时间、院系范围、该时段可预约座位数和不可用原因；可用数根据实际限制计算，不能用登记座位总数代替。整室维修时，该时段可预约数为0。外院系专属空间不提供预约入口，绕过入口提交同样会被拒绝。

学生可组合日期、时段、区域、空间、座位编号和插座条件搜索。插座分为固定插座、移动导轨插座、无插座三种，座位上应有明确标记。筛选“固定或移动插座”时，只返回所选时段可用且符合插座条件的座位；取消筛选后可以看到符合其他条件的无插座座位。被占用、停用或不满足其他可用条件的座位不能混入可预约结果。

<a id="req-m1-003"></a>
<a id="req-m1-004"></a>
### 3.2 选择时段并提交预约

学生选择座位、开始和结束时间，确认后提交。开始、结束必须为整点，单次至少1小时，默认最多4小时；管理员可将单次上限调整为1—8小时。开始时间必须晚于系统当前时刻，且不超过未来7天。非整点、零时长、过去时段或超过上限的申请应被拒绝，并指出具体原因。

预约必须完整落在开放时间内，空间和座位均有效，学生满足院系范围，且整个时段没有停用、个人预约、整室占用或维修限制。系统在提交时重新检查这些条件；搜索结果只反映查询当时的情况，不能保证提交时仍有空位。

同一座位的重叠时段只能有一个成功预约；同一个人同一时段只能有一个有效个人预约。前一个预约结束时恰好开始的下一预约可以提交。多人同时抢同一座位，或个人与整室申请同时争用资源时，系统应保留先成功的合法占用，其他操作收到冲突原因。重复提交同一次预约只返回原结果，不新增预约。

成功后状态为“已预约”，显示预约编号、空间、座位和起止时间，用户能在本人记录中找到该预约。时长上限等参数调整只约束新申请，不使此前合法预约失效，历史能够查明该预约采用的规则版本。同等权限、同样条件执行相同规则，管理员或整室申请不能挤掉已经成功的个人预约。

<a id="req-m1-005"></a>
### 3.3 取消本人预约

预约人可以在开始前取消“已预约”记录，系统保留取消原因和时间，不记违约，并解除这条预约的占用。座位是否重新可预约仍取决于其他限制。重复取消不会额外解除其他占用。

他人不能取消该预约。预约已开始或已签到后，本人不能取消；管理员也不能借普通取消操作任意擦除违约。维修、停用等导致的系统取消按第7.4节处理。

<a id="req-m1-006"></a>
<a id="req-m1-007"></a>
### 3.4 查看教室编码并签到

每间教室每天0点生成当日随机签到编码，同日不同教室不共用编码。完整编码仅在获授权的教室显示屏页面和管理人员页面显示，普通学生查询空间或预约时不能读到完整编码。

预约人到签到页面输入该教室当日编码。本人、有效预约、正确教室编码和签到时段必须同时满足。签到区间从开始前15分钟起，到开始后15分钟之前结束：09:00开始的预约，08:45可签到，09:14:59仍可签到，09:15整不再允许。不能因为取消状态尚未显示而在截止后签到。

编码按实际签到日期检查。00:00开始的预约，在前一天23:45起可使用前一天当时有效的编码；跨过0点必须改用新一天编码。昨日编码、其他教室编码、他人预约或已系统取消的预约均不能签到。

成功后记录签到时间，状态变为“已签到”，不再触发未签到提醒或违约。重复签到返回原成功结果，不改变首次签到时间。

<a id="req-m1-008"></a>
<a id="req-m1-009"></a>
<a id="req-m1-010"></a>
<a id="req-m1-013"></a>
### 3.5 提醒、未签到取消与到期完成

仍有效且未签到的预约按以下时点处理：

- **开始前15分钟**：邮件提醒空间、座位、起止时间和签到入口。预约创建时已经过了该提醒时点的，不补发这一轮提醒。
- **开始后10分钟**：再次检查仍未签到且未取消时，邮件提醒还剩5分钟，明确实际截止时刻；发送前已签到或取消的不再发送。
- **开始后15分钟**：仍未签到则自动变为“未签到取消”，解除这条预约占用，向本人发送取消邮件，并记录一次违约。同一预约最多一条有效违约，重复自动处理不能重复扣记或解除其他限制。
- **预约结束时**：已签到预约自动变为“已完成”，解除该预约占用，不新增违约。未签到记录应先按15分钟截止处理，不能到结束时直接改成已完成。

邮件投递暂时失败不妨碍取消、释放座位或记录违约；通知恢复后按同一事件补送，投递规则见第8.2节。维护导致的取消和违约豁免见第7.4节。

<a id="req-m1-011"></a>
### 3.6 查询历史与再次预约

学生可以按日期、空间和状态查询本人预约历史，看到原预约时间、签到情况、取消时间和原因、关联违约。不能查询他人的预约明细。

选择“再次预约”时，系统带出原座位，由用户选择新的时段，再按当前全部规则提交，成功后形成新的预约编号。旧记录保留，旧占用不会被复制；原座位已停用或新时段不可用时，应明确拒绝并说明原因。

<a id="req-eth-003"></a>
### 3.7 违约查询、申诉与纠错

本人可以查看违约对应的预约、应签到截止时刻及认定依据，对同一违约提交一次1—1000字的文字申诉。他人不能代该用户提交申诉。

授权运营管理员根据原预约、签到及维护等操作记录人工决定保留违约或冲正，填写理由并通知本人。合法违约保留，维护误记等错误应冲正；冲正保留原记录和处理过程，不改写原始发生时间。系统不因违约自动封禁账户或实施信用惩罚。

## 4. 整教室预约审批

<a id="req-m2-001"></a>
<a id="req-m2-002"></a>
### 4.1 申请资格与提交

仅有效校内账户中已获整室申请权限、且有权访问目标空间的申请人可以提交。普通学生默认没有整室申请权限，需要管理员授权；授权和撤销均保留记录。无权限或已撤权者即使直接提交，也不能产生申请或占用。

申请人填写房间、整点开始和结束时间、1—500字的用途、人数及联系人。人数为1至房间容量的整数，单次1—8小时，至少提前1小时，最多提前14天，并完整符合该房间开放及访问范围。缺用途、人数超过容量、提前量或时段不合法时，指出具体字段原因。

提交成功后显示申请编号、“待一级审批”和总审批截止时刻。截止为“提交后24小时”与“预约开始”中的较早者，一级通过不延长截止。待审批不占用教室，多份待审批申请可以选择重叠时段；页面预检发现可用也不保证最终批准。申请提交后不能编辑，需要先按规则撤销，再重新提交。

<a id="req-m2-003"></a>
<a id="req-m2-004"></a>
### 4.2 两级审批与批准条件

授权教室管理员在本管理范围的待办中处理一级审批，记录意见、本人身份和时间。通过后申请转为“待二级审批”，此时仍不占用教室。授权运营管理员处理二级审批，二级审批人必须与一级不同，且两级均不得由申请人本人担任。超范围、超时、跳级审批和借多角色自审均拒绝；重复处理同一次审批不增加审批级次。

二级同意后，申请先显示“占用处理中”。系统重新核对申请资格、房间开放及完整时段的全部限制，只有成功取得整室占用才显示“已批准”。已有个人预约、其他整室占用、维修或停用冲突时，申请显示“资源冲突”，保留审批意见及冲突原因，已有合法记录不被删除或挤占。

占用结果暂时无法确认时，继续显示处理中或核验中，不能提供可使用的批准凭据。批准后，整室占用覆盖该室全部有效座位，也约束之后新登记的座位；具体资源关联见第7节。

<a id="req-m2-008"></a>
### 4.3 进度、审批轨迹与结果

申请人查询本人申请，审批人查询授权范围的待办和记录。详情显示申请内容、两级审批人及其意见和时间、总截止时刻、占用确认情况，以及驳回、撤销、终止、系统取消或资源冲突的原因。无关用户不能读取这些明细。

审批待办和关键结果通过邮件通知相应人员；邮件不得夹带其他申请人的私密联系信息。页面和邮件中的申请编号应能对应同一记录。

<a id="req-m2-005"></a>
<a id="req-m2-006"></a>
<a id="req-m2-007"></a>
### 4.4 驳回、超时、本人撤销与管理终止

**驳回。** 任一级审批人只能在待该级审批阶段填写1—500字原因驳回。驳回终止后续审批，向申请人通知结果，清除该申请可能留下的占用。正常待审批本来没有占用时，不新增限制，也不能解除其他申请或个人预约的占用。

**超时。** 总审批截止到达后，尚未获得有效批准的待一级或待二级申请自动“超时撤销”。如果截止时仍在确认占用结果，应显示“核验中”，不能凭一次暂未查到记录就认定撤销。有效批准时刻以系统完成最终资格与冲突判定所记录的时刻为准，且该判定必须最终成功生效；在截止前完成判定并最终成功的，不因结果保存完成或页面收到响应较晚而误撤销。判定最终失败则没有批准事实，截止及之后也不能开始新的有效批准判定。已撤销或已因维护失效的申请不能被晚到结果恢复。最终超时撤销应通知申请人，只解除本申请的占用。

**本人撤销。** 申请人可以在预约开始前撤销本人待审批、占用处理中或已批准申请。系统受理一个新的撤销时，当前时刻必须严格早于预约开始；开始时刻及之后，所有这些阶段均拒绝新的本人撤销。即使页面仍显示占用处理中、批准结果尚未送达，也不能例外。开始前已经明确受理的同一次撤销，可以在开始后继续重试和恢复；不能借重试名义发起新的撤销。撤销完成前显示处理中，成功后保留原申请及撤销历史。

**管理终止。** 授权运营管理员可以说明原因终止已批准申请。终止同样保留历史，解除的仅是该申请占用，不影响其他预约、维修或停用限制。

### 4.5 开始使用与结束

整室申请只有在显示“已批准”并确认占用有效后，才可作为该时段使用教室的依据。预约开始本身不跳过审批，也不允许申请人发起新的本人撤销。

已批准申请到结束时自动转为“已结束”，不再占用教室。取消、终止和到期操作即使重复执行，也不能多次解除占用或影响其他来源。维护对已批准和待审批申请的影响见第7.2、7.4节。

## 5. 物业报修与维修

<a id="req-m3-001"></a>
### 5.1 上报故障

有权访问该空间的校内用户可以填写房间、可选座位、故障类别、描述和联系方式。故障类别为设施、电力、环境、其他，描述为1—1000字。提交前提示不要填写无关敏感信息。本期采用文字报修，不要求上传附件。

系统检查房间和可选座位已有效登记、座位确属该室、上报人有访问权限，合法后生成工单编号、“已提交”状态和上报时间。空描述、错误房座归属或无权空间均拒绝。已被预约或正在维修中的有效座位仍可以报修；如果当前无法核验房间、座位或权限，应提示可重试，不能先创建未经核验的工单。

提交报修本身不封锁教室、不减少可预约数。系统可以提示同室已有未结束工单，但不能强制合并报告。

<a id="req-m3-002"></a>
<a id="req-m3-010"></a>
### 5.2 查询进度、取消与误报关闭

上报人可以查询本人工单，教室和运营管理员查看授权范围工单，维修人员查看本人被派工单。详情显示进度、处理记录、当前状态及超时升级标记。无关学生不能获取工单明细或联系方式。

工单仍为“已提交”、尚未派单时，上报人可以填写原因取消；派单后不能本人取消。授权管理员可在“已提交”或“已派单”且未开始维修时，以误报、重复等原因关闭并通知相关人员。取消或关闭都保留历史及原因。

已经维修中或待验收的工单不能直接关闭，必须继续完工、验收流程。不能跳过派单直接开始或完工，也不能将上报记录直接改成已验收。系统存在开始、验收或恢复中的处理阶段时，还须遵守第5.4、5.6节的操作限制。

<a id="req-m3-003"></a>
### 5.3 派单与改派

授权教室管理员在工单派单页面按房间查找有效维修候选，可以搜索、分页选择，看到必要的用户编号、姓名和该室维修资格摘要；不需要事先知道维修人员编号，也不需要拥有系统账户管理权限。候选列表不显示邮箱、密码等无关信息。

管理员将“已提交”工单派给候选人，系统记录派单人和时间。开始维修前，可以填写原因改派，保留连续的派改历史，并通知新旧维修人员；改派后原维修人员不能再开始这项维修。

查询结果只代表查询当时的资格。派单和改派提交时，系统均须重新检查候选账户当前有效，并确有该室维修权限，不能用管理员自己的资格代替候选人的资格。普通用户、停用账户、超范围人员或查询后已经失去资格者均不能被派单。候选查询或资格核验暂不可用时，提示可重试，保持原派单与状态，不发送成功通知。派单和改派本身都不建立或解除维修封锁。

<a id="req-m3-004"></a>
<a id="req-m3-005"></a>
### 5.4 开始维修、更新进度与提交完工

本人被派维修人员选择开始维修后，系统先确认该工单对应的整室预约限制已经生效，再显示“维修中”、允许实际开始维修并通知上报人。生效时间采用系统实际确认建立限制的时刻，不能用用户设备时间倒填。整间教室全部座位均受限制，原有预约按第7.2、7.4节处理。

暂时无法确认限制时，显示“开始处理中”，不能显示已经安全封锁或允许通过其他状态绕过限制。恢复后，同一工单只能形成一份对应的有效限制。

维修中，仅当前被派维修人员可以填写1—1000字的文字进度。完工时必须填写1—1000字处理说明，成功后转为“待验收”，并向授权教室管理员和上报人发送完工通知。其他人写进度、空说明完工或跳过派单提交完工均拒绝。待验收仍保持封锁，不能因为提交完工或预计维修时间已到而自动恢复。

开始处理中、验收处理中及其恢复阶段，不接受新的派单、改派、取消、关闭、开始、进度、完工或验收操作，只能查询以及重试、恢复已经受理的原操作。即使另一操作者刷新到了最新状态，也不能绕过这一限制。后台仍可记录超时升级和操作轨迹，但不能改变已经受理的业务决定。

<a id="req-m3-006"></a>
### 5.5 超时升级与跟进

工单提交后4小时仍未派单，自动标记派单超时；从首次开始维修起24小时仍未验收，自动标记维修超时。标记应记录超时类型和应到期时间，向授权运营管理员、教室管理员及该事件发生时记录的维修人员发送邮件；未派单时没有维修人员收件人。

同一工单每种超时只触发一次，返修不重置首次维修计时。升级不改变“已提交”“维修中”或“待验收”等主状态，不解除封锁；以后派单或验收也不删除已发生的升级历史。管理员可以查看标记并据此跟进。

管理员收件人按通知解析时的房间当前归属及账户授权范围确定，例如仅具院系甲管理范围的管理员不能收到院系乙工单升级。维修收件人采用升级事件当时记录的人员，重试时不换成后来改派的人，但发送时仍检查该账户有效；同一人兼任管理员和维修人时，该事件不重复投递给此人。发起人退出登录不影响后台通知，范围事实暂无法核实时按第8.2节保持待处理，不能用不完整名单冒充已通知。

<a id="req-m3-007"></a>
### 5.6 人工验收、返修与恢复

授权教室管理员在工单“待验收”且没有其他处理中操作时，可以选择通过或不通过，并填写1—1000字说明。验收人不能是该工单维修人员。不通过后回到“维修中”，保留原维修限制，由维修人员继续处理，再次提交完工后重新验收。

验收通过决定一经系统确认受理，就进入“验收处理中”，本轮决定随即固定。系统只解除本工单对应的限制，核实完成后才显示“已验收”，并向上报人发送验收完成通知。解除暂时失败或解除结果尚未确认时，继续显示处理中，不能提前声称已经恢复。

验收处理中只能查询、重试同一通过决定或恢复原操作，不能提交相反决定改成返修，也不能进行第5.4节列出的其他新操作。另一位有权限管理员即使读取最新状态，以新操作提交不通过也应拒绝；不能形成“已经回到维修中却没有本工单封锁”的结果。

如果预约限制已经解除，但工单页面尚未收到确认，预约可用性按实际剩余限制计算，工单仍显示验收处理中，直到查证同一次解除结果。验收成功不等于整室一定可预约，其他维修、停用或占用仍须保留，见第7.3节。

<a id="req-m3-008"></a>
### 5.7 完工评价与历史可见

工单已验收后7天内，上报人可以提交一次评价：1—5的整数评分，以及可选的不超过500字文字。待验收、超过7天、他人代评、重复评价、非整数或超出评分范围均拒绝。未评价不妨碍解除维修限制。

管理员和维修人员可以在各自授权范围查看评价，不能代写或修改。工单的上报、派改、进度、完工、返修、验收、超时、取消或关闭记录应按第5.2节的查看范围保留，能够连续查询。

## 6. 管理功能

<a id="req-d-003"></a>
<a id="req-d-004"></a>
### 6.1 空间、院系与座位管理

授权教室管理员登记和维护本范围空间，包括唯一空间编号、名称、地点、类型（普通教室、图书馆、其他）、容量、全校开放或单一院系归属、有效状态。重复编号不能登记。空间注销采取停用并保留历史的方式，历史预约仍能显示原空间编号和名称。

管理员在座位管理页可以分页浏览授权房间全部登记座位，包括停用或被占用的座位，按座位编号、状态查询，看到当前维护信息及允许操作；不需要预先知道座位编号才能发现待维护对象。这一管理能力不使普通学生搜索到可预约的停用座位。

座位资料包括唯一座位编号、所属空间、有效状态和固定插座、移动导轨插座、无插座标记。管理员可以新增座位和调整插座标记，重复编号拒绝。已经产生历史的座位不允许改编号或迁入另一房间；需要变更位置时，注销旧座位并登记新座位，保留原签到和预约历史，避免房座错配。注销有占用的空间或座位须遵守影响确认规则。

<a id="req-d-005"></a>
### 6.2 开放时间、停用与恢复

授权教室管理员可配置每周开放时段和指定日期例外，指定日期例外优先；例如平时08:00—22:00开放，某日例外10:00—18:00，该日09:00不可预约，预约也不能跨出18:00。

管理员可以对房间或座位设置带原因的停用区间，并在需要时结束该项停用。结束停用只解除这一项管理员限制，不能一并解除维修、其他停用或预约占用。空间或座位无效时不得接受新预约。

### 6.3 变更影响预览与确认

缩短开放时间、设置停用、注销空间或座位前，系统向授权操作者展示受影响的未结束记录及原因，确认后再按第7.4节处理，不得悄悄改变已成功预约。

将空间从全校开放改为某院系专属等归属调整，也须预览和确认受影响记录；不再符合范围的未结束记录整条系统取消，保留原历史。系统取消不额外惩罚用户，已到签到截止形成的违约仍按第7.4节判断。未失去资格的记录和其他房间不应受影响。

<a id="req-d-006"></a>
### 6.4 账户、角色与业务参数

系统管理员维护校内账户的用户编号、姓名、院系、联系邮箱和有效状态，配置角色、操作权限及空间范围；普通用户不能自行选择院系或角色。登录及改密规则见第8.1节。

系统管理员可以在允许范围内调整个人预约时长上限、提前窗口、自动检查间隔和通知重试等参数。个人单次上限仅允许1—8小时，0或9等非法值应拒绝；普通用户不得改参数。提醒时点、固定两级审批等基线规则不能通过普通参数操作任意更改。

每次变更保留参数版本、操作者和生效时间，不追溯改写既有合法申请所用规则。例如个人上限从4小时改为3小时后，新申请最多3小时，原合法4小时预约继续有效，历史仍能说明其采用的规则。

<a id="req-m1-012"></a>
### 6.5 预约统计与指标说明

授权运营管理员可按日期、房间查询座位预约明细、已签到数、未签到违约数、系统取消数和预约占用率。无权限或超出管理范围的查询拒绝。未来时段只展示预约数和明细，占用率只计算截至查询时刻已经发生的区间。

预约占用率的分子，是个人预约实际有效占用与预约时段、已发生查询区间交集的座位分钟数；分母是同一区间按当时开放规则，扣除停用、维修及整室占用后的可供个人预约座位分钟数。分母为0时显示“不适用”。页面应说明口径，并能够查明当时的开放、限制及占用实际建立和解除时间，不能用记录现在的最终状态抹掉过去确实生效的占用。

例如，一小时内2座位可供个人预约，共120座位分钟，其中1座位有效占用60分钟，占用率为50%。另一个独立例子中，仅统计一个座位：一小时内先有效占用30分钟，随后因维修取消并封锁剩余30分钟，分子、分母均为30，占用率仍为100%，不能因系统取消把分子改为0。已签到数仅表示完成签到，不能解释为实测在座人数或时长。

<a id="req-d-008"></a>
<a id="req-d-009"></a>
### 6.6 操作记录与资源状态追溯

系统记录账户、权限、参数、空间和座位变更，以及预约取消、签到、违约、审批、工单处理、限制建立和解除等关键动作。记录包含操作者或系统自动任务、时间、动作、对象编号、前后状态、原因、关联编号和结果，能够区分成功与失败。授权管理员可以在管理范围内按对象、时间查询并关联同一业务过程，业务人员不能修改或删除这些记录。

管理员可以查询指定座位、时段为何可用或不可用，看到个人预约、整室占用、维修、管理员停用等来源类型、来源编号、生效区间、建立和解除原因，以及关联的操作记录，并进入有权查看的源记录。已解除的来源仍可追溯。学生只看到不可用类别和可用情况，不显示他人身份或用途。记录不得泄露密码、完整签到编码或不必要的私人描述。

<a id="req-int-004"></a>
<a id="req-eng-009"></a>
### 6.7 运行信息、异常事项与恢复

管理员可在系统运行信息中查看当前正在运行的版本，便于报告和核对问题。

有相应查看或恢复权限的管理员，可以按状态、时间、业务来源、房间和管理范围筛选、分页查看尚未完成的审批占用、维修开始、验收解除等异常事项，不需要预先知道操作编号。清单显示来源对象、关联编号、错误原因、下次重试时刻、当前记录信息和允许的恢复操作；管理员可以查看详情并受控重试，不能借恢复权限改动无关业务或绕过范围检查。

通知异常另有失败或结果未知清单，授权管理员可以从清单发现通知、查看投递尝试、收件及失败信息并重试，即使本人不是收件人也不必预知通知编号。无权限或超范围者不能看到他人的投递详情。

异常概览显示同一授权范围内的积压数、最早未处理事件已等待时间、失败投递数和待恢复操作数，统计必须与对应清单使用相同口径。问题不能静默丢失；自动恢复时限及用户反馈见第8.3、8.4节。

## 7. 业务关联规则

<a id="req-m2-009"></a>
<a id="req-int-001"></a>
### 7.1 个人预约与整室占用的冲突

个人预约和整室申请使用同一套可用性规则。整室待审批不预先锁座，多个申请可以重叠；最终批准时才检查并取得整间教室的占用。该占用覆盖该室全部有效座位，批准后新增的座位也受同一整室时段约束。

同室重叠时段的个人预约和整室占用不能同时成功，多份整室申请也只能有一份取得冲突范围的有效占用。先成功的合法记录保留，其他申请明确显示资源冲突；不得以管理员身份或整室用途为由删除原个人预约。整室撤销、终止或到期仅解除该申请占用，资源没有其他限制时才重新可预约。

<a id="req-m2-010"></a>
<a id="req-int-002"></a>
### 7.2 维修对新预约和存量记录的影响

报修或派单不直接改变可预约数；确认开始维修后，整间教室全部座位受对应工单的维修限制，包括后续新增的座位。维修限制从实际建立时刻起持续到验收通过并解除该项限制，没有预计结束时间自动放行；在其仍生效时，不得接受涉及未结束时间范围的新预约。

维修影响的未结束个人预约和已批准整室申请按第7.4节整条系统取消，不部分截短或自动改签。待审批整室申请保留已有意见，但最终批准时必须重新检查，维修未解除则资源冲突。其他房间的记录不受影响。

维修限制一旦实际生效，预约页面立即按受限结果拒绝新预约，即使某个申请详情还在处理中。状态恢复后，该详情应与实际生效结果一致；受影响的原申请不会因较晚到达的批准结果重新生效。

<a id="req-m3-009"></a>
<a id="req-int-003"></a>
### 7.3 多项限制与验收后的可用性

座位可预约必须同时满足：空间和座位有效、用户符合院系范围、完整覆盖开放时段，且没有冲突的个人预约、整室占用、管理员停用或维修限制。不同来源独立存在，解除一项不能覆盖其他项。

同室两份维修工单各自建立、解除自己的限制。先验收第一份，第二份仍维修，教室继续不可预约；再验收第二份，若仍有管理员停用，仍不可预约；全部相关限制解除后才按开放和预约情况恢复。详情能够列出每个生效来源及历史，不能仅凭某份工单页面显示“已验收”就判断整个教室空闲。

验收解除已经实际完成而确认尚未显示时，资源按实际剩余来源判断，工单保持“验收处理中”直到核实；不能提前宣称已经恢复，也不能改判返修。重复、晚到的取消或解除操作，只能影响原来源，不能删除后来建立的限制。多个相互冲突的操作最终必须得到一个合法结果，并保留原因和发生顺序。

<a id="req-m1-014"></a>
### 7.4 系统取消、违约豁免与历史保留

维修开始、管理员停用、空间或座位注销、开放时间缩短等变更，与有效记录冲突时，系统对受影响且未结束的个人预约、已批准整室申请整条取消，保留维护来源、原状态、生效时刻和原因，解除各自占用，并通知相关人员重新选择资源。院系归属变化使原记录失去资格时，同样保留历史并系统取消。取消不做部分截断或自动改签。

维护本身不新增违约。对于未签到预约，必须比较原签到截止与维护实际生效时间：

- 维护早于签到截止，按系统取消处理并豁免这次未签到违约；若之后误记，关联原记录冲正。
- 签到截止早于或等于维护生效时间，先按该截止判定“未签到取消”并保留一次违约，不能因为自动检查尚未运行而改成豁免。

例如09:00开始且始终未签到的预约，维修09:14:30生效时豁免；09:15:00或09:15:30生效时，均已触及09:15截止，保留一次违约。先处理维修还是先处理到期，不应改变结论。原截止、实际处理时间和冲正关系可查；维护前已经成立的违约和已经完成的记录不追溯删除。

取消后的预约、申请和工单历史继续按原有权限可见，不能通过删除记录掩盖取消原因或已发生占用。恢复开放或维修解除后，原记录不自动复活，用户需要重新申请。

<a id="req-int-005"></a>
### 7.5 各页面结果一致

各页面使用同一身份、空间、座位、预约、申请、工单和来源编号关联记录。同一资源同一时段的可用性、同一业务的权限和最终结果，应在搜索、预约、审批、报修、管理及历史页面保持一致，不能在某个入口绕过规则。

信息尚未确认时，页面明确显示处理中或核验中及关联编号；确认后更新为对应结果。无权操作、无效对象、冲突、超时和重复操作均应有一致、可理解的反馈，不得用某一页面暂时未刷新作为继续使用或解除限制的依据。

## 8. 通用体验与质量要求

<a id="req-d-001"></a>
### 8.1 登录、退出与修改密码

用户使用系统管理员导入或维护的校内账户登录。正确凭据且账户有效时进入本人身份对应的功能；错误密码或停用账户不能登录，不能向其他用户返回密码等凭据。退出登录或账户被停用后，原登录状态不能继续提交业务操作。

初次登录无需强制修改密码，正确凭据且账户有效时即可按已有权限使用。用户可主动修改密码，新密码为 8—24 个 Unicode 字符；改密页面和后端核验当前密码、新密码长度及两次输入一致性。旧凭据在用户修改前继续有效，不因长度规则调整而自动重写。该规则由用户于 2026-11-02 调整，详见 [认证调整记录](../docs/decisions/G5-006-password-policy.md)。

合法改密后，该账户全部原登录状态失效，旧密码不能再登录；用户须用新密码重新登录，再按原有权限操作。页面、通知和操作记录均不显示或保存密码正文。

<a id="req-d-007"></a>
### 8.2 邮件通知与失败反馈

系统实际发送邮件，覆盖个人预约提醒和取消、整室审批待办及结果、维修派改、完工、验收、升级和维护影响。通知应能对应业务记录，记录事件编号、收件人、投递状态、重试及失败原因。只有业务结果成立后才发送相应成功通知，不得在验收仍处理中时先发送恢复成功。

每类事件按固定规则确定收件对象。预约人、申请人、上报人、维修人等业务参与人采用事件发生时记录的人员，发送前再核验账户有效；按空间寻找的管理员，按解析通知时的当前房间归属、有效账户及当前权限范围确定。不依赖发起人的登录状态。同一人同时符合参与人和管理员条件时，对同一事件只安排一份投递。

如果核对必需的房间归属或管理范围暂时失败，整份收件解析继续待处理，不能只通知已知的一部分人便记为成功，也不能把空名单记为成功。确认确实没有合格收件人时，明确标记需关注，供有权限管理员处理。

投递失败自动重试最多5次，仍失败时进入授权管理员可查询和手动重试的清单。通知失败不撤销已经成立的预约、取消、批准或维修结果；重试同一事件也不能重复业务操作。已确认投递成功的事件不再次发送。

邮件发送结果未知时，应在记录中说明“结果未知，可能重复”，后续重试可能产生带同一事件编号的重复邮件。系统不承诺邮件传输绝对只到达一次，但必须让收件人及有权限管理员辨认它们属于同一事件。失败清单及查看权限见第6.7节。

<a id="req-m1-015"></a>
### 8.3 空态、错误与处理中状态

没有搜索结果、没有历史或没有待办时，页面明确说明当前无记录，并提供适合的下一步入口。字段不合法应指出对应字段及原因；座位被抢占或时段冲突，应说明冲突类别，便于重新选择。

登录过期时提示重新登录；业务暂不可用、断网或结果未确认时，说明可重试或核验的方式。处理中、核验中均显示关联编号，供本人查询或管理员查找。不能仅用按钮动画、请求已发送或页面跳转表示成功；成功应有可查询的编号记录。无法核验整室占用时，不提供可使用的批准凭据；无法确认维修开始或验收解除时，不显示已经安全封锁或已恢复。

### 8.4 重复提交、冲突与故障恢复

用户反复点击、重试同一操作，或系统重启后重新处理，都不能创建多份预约、重复审批占用、重复违约或重复建立、解除限制；同一已成功操作返回原结果。旧操作的较晚结果不能覆盖新的合法状态，也不能恢复已经撤销或系统取消的记录。页面内容已被他人更改时，不能继续用旧内容覆盖新结果，应提示刷新后核对；刷新仍不能绕过处理中或回避等限制。

多人同时操作、签到与截止相遇、批准与维修相遇、本人取消与系统取消相遇时，应按权限、实际生效时间和各业务边界得到一个合法结果，保留可解释的原因与先后关系。不能出现冲突占用同时成功、维修中被错误开放，或通过重复提交绕过开始后撤销禁令、验收决定冻结等规则。

故障期间不虚报成功。相关功能恢复后，系统应在5分钟内自动完成待处理事项，或明确标为失败、需人工处理；预约、申请和工单状态须与实际占用、限制一致。仍未完成的事项进入第6.7节授权清单，能够发现、说明原因和受控恢复，不能静默消失。

### 8.5 手机、电脑与响应

学生主要流程在手机浏览器和电脑浏览器均可完成，包括搜索、预约、取消、输入签到编码和历史查询。在390像素宽手机页面上，核心字段、状态和按钮不能被横向遮挡；管理页面在电脑上可以完成审批、派改、验收、配置及统计。

提交后应显示结果或明确处理中反馈，长时间处理不能让用户误以为已成功。自动时点按第1.4节处理，故障恢复按第8.4节处理；页面反馈不能放宽各业务截止。

### 8.6 隐私、规则透明与数据保留

系统只采集必要的校内身份、院系、联系邮箱和业务内容，不收集精确定位、生物识别或其他无关敏感资料。报修填写处提示勿提交敏感信息。用户记录按本人、职责和空间范围访问，维修人员仅见必要联系信息；操作记录及公开演示材料应脱敏，真实个人数据不进入公开仓库或公开展示。

用户在申请前能够了解预约时长、院系限制、签到截止和违约、审批及维修规则。不可用结果说明类别，统计说明计算口径；同等权限和条件适用相同规则。签到数据仅表示完成编码签到，不宣称能证明实际物理在座。

传输和备份受到保护，只有授权维护人员可以取得运行凭据或访问备份。系统每日备份一次，保留7天，备份应能用于恢复并核对业务记录。业务及操作记录在课程部署期间保留至课程结束后90天，到期后由授权人员执行删除或不可逆匿名化，只保留不含身份的汇总。

到期清理必须覆盖备份；即使某份旧备份尚在7天保留期内，也不能再从中恢复到期身份。清理结果保留可查记录。普通用户不能直接擦除操作审计，也不能通过取消预约或关闭工单删除业务历史。
